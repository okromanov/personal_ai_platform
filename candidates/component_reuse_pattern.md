# Переиспользование зрелых компонентов для ARC_CMP_006 и ARC_CMP_008

## 1. Назначение

Документ фиксирует рекомендацию по методу реализации, а не решение владельца. Она возникла как вывод сравнения архитектуры платформы с внешними агентскими харнессами и библиотеками и подготовлена заранее, чтобы не потеряться между сессиями — по тому же принципу, что [`skill_lifecycle.md`](skill_lifecycle.md), [`tool_lifecycle.md`](tool_lifecycle.md), [`agent_roles_and_delegation.md`](agent_roles_and_delegation.md) и [`family_multi_user_candidate.md`](family_multi_user_candidate.md).

В отличие от трёх из них, это не кандидат нового `BR_*` вне V1: [`ARC_CMP_006`](../specifications/architecture_baseline.md#arc_cmp_006) и [`ARC_CMP_008`](../specifications/architecture_baseline.md#arc_cmp_008) уже в периметре V1 через [`BR_022`](../specifications/business_requirements.md#br_022)–[`BR_024`](../specifications/business_requirements.md#br_024) и [`BR_027`](../specifications/business_requirements.md#br_027) (все `core`) и назначены на [`m04`](../milestones.md#m04) и [`m03`](../milestones.md#m03) соответственно. Документ не выбирает конкретный компонент и не решает архитектуру — по [`AGENTS.md`](../AGENTS.md) список кандидатов для ADR согласуется с владельцем до создания файла ADR, а для [`m03`](../milestones.md#m03) ADR в плане вообще не предусмотрен: выбор компонента там относится к TASK-уровню при декомпозиции этапа.

## 2. Рекомендация

Для памяти ([`ARC_CMP_006`](../specifications/architecture_baseline.md#arc_cmp_006)) и для проверки качества результата ([`ARC_CMP_008`](../specifications/architecture_baseline.md#arc_cmp_008)) на рынке есть зрелые готовые компоненты — memory-движки с автоматическим извлечением и консолидацией долговременных фактов, guardrails/eval-фреймворки для проверки вывода модели. Строить это с нуля дороже и, вероятнее всего, менее надёжно, чем то, что уже проверено на масштабе за пределами проекта. Реализация не обязана начинать с чистого листа.

Но оба требования несут архитектурные инварианты, которых типичная сторонняя реализация не соблюдает по умолчанию:

- **Explicit consent на память.** [`ARC_CMP_006`](../specifications/architecture_baseline.md#arc_cmp_006) запрещает источнику, доказательству или выводу модели автоматически становиться долговременной памятью и требует приоритет исправления/удаления владельцем над прежним выводом системы ([`SEC_CTL_019`](../specifications/system_specification.md#sec_ctl_019)). Типичный сторонний memory-движок по умолчанию делает обратное — автоматически консолидирует разговор в факты без отдельного шага подтверждения.
- **Security ≠ eval.** [`ARC_CMP_008`](../specifications/architecture_baseline.md#arc_cmp_008) и [`SYS_023`](../specifications/system_specification.md#sys_023) требуют, чтобы недетерминированная оценка (LLM-as-judge, guardrail-проверка) могла улучшать качество, но не подменяла разрешения безопасности и доказательства восстановления/целостности. В типичных eval-библиотеках это разделение не структурное правило, а вопрос того, как их подключил интегратор.

**Метод:** выбранный сторонний компонент подключается через контракт [`ARC_CMP_006`](../specifications/architecture_baseline.md#arc_cmp_006)/[`ARC_CMP_008`](../specifications/architecture_baseline.md#arc_cmp_008) так, что решение «это стало долговременной памятью» и решение «этот результат прошёл проверку безопасности» остаются explicit-шагами платформы, а не побочным эффектом библиотеки. Библиотека отвечает за исполнение (извлечение, хранение, оценку); платформа — за то, что из этого исполнения становится обязывающим фактом или разрешением.

## 3. Что этот документ не решает

- Конкретного кандидата для памяти или для проверки качества результата — рынок и конкретные названия здесь намеренно не приводятся: сравнение происходит на момент реализации, по [`project_rules.md`](../project_rules.md) Принципу 19, не сейчас и не этим документом.
- Схему хранилища памяти — это предмет [`ADR_008`](../adr/adr_008_data_storage_schema.md#adr_008), который уже `proposed` и уже трассируется на [`BR_022`](../specifications/business_requirements.md#br_022)–[`BR_024`](../specifications/business_requirements.md#br_024); эта рекомендация — дополнительный контекст для сравнения кандидатов там, а не замена его содержания.
- Нужен ли отдельный ADR для реализации [`ARC_CMP_008`](../specifications/architecture_baseline.md#arc_cmp_008) — текущий план [`m03`](../milestones.md#m03) ADR не предусматривает; если при декомпозиции этапа выбор компонента окажется стратегическим (вендорлок, критичная зависимость), решение о том, нужен ли для него отдельный ADR, принимает владелец в диалоге, а не этот документ.
