# Базовая логическая архитектура personal_ai_platform

## 1. Назначение

Документ отвечает на вопрос: **из каких устойчивых логических частей состоит система, за что каждая отвечает и как между ними проходит взаимодействие**.

Он не определяет план этапов, состав версии, физическую облачную топологию или конкретную среду агента и поставщика. Выбранный механизм фиксируется в ADR только после фактического выбора.

## 2. Архитектурные принципы

1. Контроль владельца и обязательные технические проверки находятся вне доверенной области модели и сменной среды агента.
2. Данные и решения принадлежат владельцу. Платформа технически управляет каноническим состоянием от его имени. Состояние не принадлежит конкретной модели, программной основе или поставщику.
3. Внешние зависимости подключаются через ограниченные адаптерные границы.
4. `Skill` описывает переиспользуемую инструкцию или многошаговый сценарий. Он запрашивает одну или несколько разрешённых `Capabilities` — устойчивых способностей пользователя или системы. `Tool` выполняет атомарную операцию внутри разрешённой `Capability`, а `Implementation/Provider` задаёт сменную привязку к адаптеру или поставщику.
5. Зависимость исполнения строится как `Skill → Capability → Tool ⇢ Implementation/Provider`. Последний переход является привязкой к реализации, а не ещё одним архитектурным объектом того же уровня. Канал связи, обнаружение инструмента или описание внешней интеграции не являются авторизацией.
6. Контекст является управляемым ресурсом. Модели передаётся минимально достаточный контекст текущей задачи.
7. Одна универсальная среда выполнения является базовой формой. Дополнительные агенты вводятся только при доказанной пользе.
8. Логическая архитектура не меняется из-за смены физического размещения, если сохраняются контракты и границы полномочий.
9. **Модульный монолит по умолчанию.** Логический компонент не означает отдельный процесс, контейнер или сервис. Пока нет доказанной потребности в иной границе, платформа развёртывается минимальным числом единиц. Физическое разделение вводится только ради изоляции, надёжности или другого измеримого выигрыша.
10. Синхронное и фоновое выполнение используют один контракт задачи. Канонический жизненный цикл, checkpoint, корреляция событий и право отмены не принадлежат сменной среде агента.
11. Подтверждения, лимиты, авторизация и аудит обеспечиваются программными контрольными точками до и после значимых этапов выполнения. Подсказка модели не является механизмом безопасности.
12. События являются способом связи частей модульного монолита, а не основанием заранее вводить отдельную распределённую шину или микросервисы.

## 3. Стабильные архитектурные компоненты

<a id="arc_cmp_001"></a>
### ARC_CMP_001 — Каналы

- `traces_to`: [`SYS_001`](system_specification.md#sys_001), [`SYS_036`](system_specification.md#sys_036), [`SYS_005`](system_specification.md#sys_005), [`SYS_006`](system_specification.md#sys_006), [`SYS_007`](system_specification.md#sys_007)

Нормализует пользовательский ввод и вывод для поддерживаемых интерфейсов. Канал не владеет бизнес-логикой задачи, постоянной памятью или полномочиями инструмента.

<a id="arc_cmp_002"></a>
### ARC_CMP_002 — Безопасность и контроль владельца

- `traces_to`: [`SYS_002`](system_specification.md#sys_002), [`SYS_008`](system_specification.md#sys_008), [`SYS_009`](system_specification.md#sys_009), [`SYS_020`](system_specification.md#sys_020), [`SEC_CTL_001`](system_specification.md#sec_ctl_001), [`SEC_CTL_002`](system_specification.md#sec_ctl_002), [`SEC_CTL_004`](system_specification.md#sec_ctl_004), [`SEC_CTL_008`](system_specification.md#sec_ctl_008), [`SEC_CTL_012`](system_specification.md#sec_ctl_012), [`SEC_CTL_015`](system_specification.md#sec_ctl_015), [`SEC_CTL_020`](system_specification.md#sec_ctl_020)

До создания задачи и вызова модели компонент проверяет личность, частоту и размер запроса, тип входных данных, доверие к содержимому, наличие инструкций из недоверенного источника, область данных, допустимость поставщика и применимые лимиты. Внешний файл, веб-страница, письмо, результат модели или интеграции остаются данными в соответствии с [`SEC_CTL_004`](system_specification.md#sec_ctl_004) и не могут изменить политики.

После входной проверки применяются правила владельца, ограничения области, требуемое подтверждение и класс воздействия. Отдельная техническая проверка повторяется перед чувствительным действием. Лимиты времени, повторов, частоты и стоимости исполняются по [`SEC_CTL_012`](system_specification.md#sec_ctl_012), а допустимость данных для модели и поставщика — по [`SEC_CTL_015`](system_specification.md#sec_ctl_015).

Аварийный выключатель имеет приоритет над средой выполнения, планировщиком, повторами, контролем работы, моделями и инструментами. Ни один из этих компонентов не имеет обходного пути к ресурсам.

<a id="arc_cmp_003"></a>
### ARC_CMP_003 — Оркестрация и RuntimePort

- `traces_to`: [`SYS_001`](system_specification.md#sys_001), [`SYS_036`](system_specification.md#sys_036), [`SYS_003`](system_specification.md#sys_003), [`BR_033`](business_requirements.md#br_033)

Преобразует нормализованную задачу с целью, входом, критериями успеха и требуемыми доказательствами в исполнимый цикл и подключает выбранную среду агента через стабильную границу `RuntimePort`. Особенности конкретной реализации остаются внутри переходного слоя. Компонент не владеет главными секретами, контролем владельца или канонической долговременной памятью.

`Skill Registry` хранит версионированные манифесты: назначение, вход и результат, запрашиваемые `Capabilities`, допустимые `Tools`, тип выполнения, модельную политику, полномочия, подтверждения, timeout, retry, checkpoint и совместимый Runtime. Исполнительная зависимость следует принципу `Skill → Capability → Tool ⇢ Implementation/Provider`.

Тип выполнения имеет одно из значений: `contextual` добавляет разрешённые знания или инструкции в контекст без самостоятельного процесса; `stateless` выполняется однократно без собственного долговечного состояния; `stateful` использует внешнее каноническое состояние задачи и checkpoint. Ни один тип не хранит полномочия внутри промпта.

Оркестратор создаёт отдельный `Run` для синхронной или фоновой задачи, умеет вернуть немедленное подтверждение постановки, получить статус, отменить выполнение и передать допустимое уточнение. Если `Quality Gate` разрешает повтор, оркестратор создаёт новый связанный `Run`, передаёт ему причину отклонения и пересматривает план относительно тех же либо явно скорректированных владельцем критериев; признанный неудовлетворительным запуск скрыто не продолжается. Программные hooks `before_task`, `before_model`, `before_tool`, `after_tool`, `before_external_action`, `before_result`, `on_error` и `on_complete` вызывают независимые проверки, но не заменяют их собственной логикой Runtime.

Лёгкая долговечная очередь и журнал событий обеспечивают доставку уведомлений, аудит, плановые запуски и восстановление. Они остаются внутренним механизмом модульного монолита, пока измеримая потребность не потребует другой физической границы.

<a id="arc_cmp_004"></a>
### ARC_CMP_004 — Шлюз моделей

- `traces_to`: [`SYS_004`](system_specification.md#sys_004), [`SYS_022`](system_specification.md#sys_022), [`BR_034`](business_requirements.md#br_034), [`SEC_CTL_015`](system_specification.md#sec_ctl_015)

Предоставляет нормализованный контракт запросов, ответов, ошибок и доступных показателей моделей. По политике задачи выбирает модель и отдельную сессию выполнения с учётом класса данных, качества, скорости, стоимости и доступного бюджета. Timeout, ограниченный повтор и fallback дают контролируемый исход и не расширяют допустимость данных для резервной модели.

Выбор поставщика не меняет контракты каналов, задач и данных и не ослабляет правила. Фактически выбранные модель, версия, адаптер и существенные метрики сохраняются в доказательствах выполнения.

<a id="arc_cmp_005"></a>
### ARC_CMP_005 — Шлюз инструментов

- `traces_to`: [`SYS_020`](system_specification.md#sys_020), [`SYS_021`](system_specification.md#sys_021), [`SEC_CTL_003`](system_specification.md#sec_ctl_003), [`SEC_CTL_007`](system_specification.md#sec_ctl_007), [`SEC_CTL_008`](system_specification.md#sec_ctl_008), [`SEC_CTL_009`](system_specification.md#sec_ctl_009)

Является единой точкой технической авторизации вызовов инструментов. Контракт возможности задаёт разрешённый субъект, ресурс, область, класс воздействия, данные, секреты, сеть, ограничения, подтверждение и защиту от дублей.

MCP и другие протоколы являются способами интеграции, а не источниками полномочий. Метаданные и сведения об обнаружении внешнего сервера остаются недоверенными данными.

Для каждого `Run` шлюз выдаёт модели только минимальный набор `Tools`, разрешённый выбранному `Skill`. Файлы, код, команды и рискованный разбор выполняются в изолированной рабочей области конкретной задачи по [`SEC_CTL_009`](system_specification.md#sec_ctl_009), с квотами, запретом секретов и сети по умолчанию, явными подключениями данных и полным журналом значимых действий.

<a id="arc_cmp_006"></a>
### ARC_CMP_006 — Контекст, память и доказательства

- `traces_to`: [`SYS_008`](system_specification.md#sys_008), [`SYS_009`](system_specification.md#sys_009), [`SYS_010`](system_specification.md#sys_010), [`SYS_011`](system_specification.md#sys_011), [`SYS_012`](system_specification.md#sys_012), [`SYS_029`](system_specification.md#sys_029), [`SEC_CTL_004`](system_specification.md#sec_ctl_004), [`SEC_CTL_006`](system_specification.md#sec_ctl_006), [`SEC_CTL_019`](system_specification.md#sec_ctl_019)

Логически разделяет рабочее состояние, разговор и сессию, профиль и цели владельца, долговременную память, граф знаний, контекст проекта и архив доказательств. Сборщик контекста формирует для конкретного `Run` разрешённую проекцию из режима, состояния задачи, проекта, релевантной памяти и доказательств.

Каждый фрагмент сохраняет область данных, происхождение, доверие и применимый срок хранения. Контекст собирается по принципу минимальной достаточности и поэтапного раскрытия. Источник, доказательство или вывод модели не превращается автоматически в долговременную память. Исправление и удаление владельцем имеют приоритет согласно [`SEC_CTL_019`](system_specification.md#sec_ctl_019).

<a id="arc_cmp_007"></a>
### ARC_CMP_007 — Состояние задач

- `traces_to`: [`SYS_001`](system_specification.md#sys_001), [`SYS_036`](system_specification.md#sys_036), [`SYS_013`](system_specification.md#sys_013), [`SYS_020`](system_specification.md#sys_020), [`SEC_CTL_008`](system_specification.md#sec_ctl_008), [`SEC_CTL_017`](system_specification.md#sec_ctl_017)

Хранит идентичность, цель, вход, версию критериев успеха, требуемые доказательства и долговечный жизненный цикл синхронной или фоновой задачи: `accepted → queued → running → waiting_confirmation → completed | failed | cancelled`. Для управляемого восстановления сохраняются checkpoint, ограниченный повтор, отмена, возобновление и защита от дублей.

Каждый `Run` получает корреляционный `runtime_task_id`. Уже совершённый внешний эффект не повторяется при восстановлении после перезапуска или сбоя — идемпотентность действия обязательна независимо от числа исполнителей. Lease исполнителя и heartbeat, защищающие от гонки между несколькими параллельными исполнителями, требуются только при более чем одном одновременном исполнителе; пока исполнитель ровно один, они не являются обязательным свойством.

События `task.accepted`, `task.started`, `task.progress`, `confirmation.requested`, `tool.started`, `tool.completed`, `task.completed`, `task.failed` и `task.cancelled` образуют проверяемую историю с минимизированными данными. Состояние задачи и журнал не являются внутренним состоянием конкретной среды агента.

<a id="arc_cmp_008"></a>
### ARC_CMP_008 — Проверка качества

- `traces_to`: [`SYS_022`](system_specification.md#sys_022), [`SYS_023`](system_specification.md#sys_023), [`BR_004`](business_requirements.md#br_004), [`BR_027`](business_requirements.md#br_027)

Оркестрирует применимые детерминированные проверки, Evals, проверку материалов, `LLM-as-a-judge` и проверку безопасности выхода. Результат сопоставляется с версией критериев успеха и требуемыми доказательствами текущей задачи. Недетерминированная оценка может улучшать качество, но не выдаёт полномочия безопасности и не заменяет проверки восстановления и целостности.

`Quality Gate` не принимает решение за владельца, а выдаёт один из четырёх типизированных переходов: проверенный результат; новый `Run` с причиной отклонения и пересмотренным планом, если автоматический повтор разрешён и лимит не исчерпан; запрос выбора владельца, если автоматической проверки недостаточно или его требует профиль качества; контролируемый исход, если повтор запрещён или исчерпан. `Выбор владельца` является условным контрольным переходом после проверки качества, а не вторым результатом проверки: подтверждение ведёт к проверенному результату, коррекция критериев или результата — к новому `Run`, остановка — к контролируемому исходу. После выбора получается ровно один конечный переход; проверка после исполнения не заменяет подтверждение до чувствительного внешнего действия.

<a id="arc_cmp_009"></a>
### ARC_CMP_009 — Эксплуатационные функции

- `traces_to`: [`SYS_013`](system_specification.md#sys_013), [`SYS_024`](system_specification.md#sys_024), [`SYS_025`](system_specification.md#sys_025), [`SYS_026`](system_specification.md#sys_026), [`SYS_027`](system_specification.md#sys_027), [`SYS_028`](system_specification.md#sys_028), [`SYS_030`](system_specification.md#sys_030)

Объединяет логическое состояние планировщика, долговечной очереди событий, корреляции по `runtime_task_id`, работоспособности, версий, резервного копирования, восстановления из checkpoint и ограниченных действий восстановления. Для запуска собираются доступные показатели времени и задержки, стоимости, итераций и повторов, ошибок и достижения критериев качества; агрегаты и репрезентативные завершённые запуски образуют вход offline eval. Вывод eval создаёт прослеживаемое предложение изменения, но политика, профиль качества или полномочия меняются только через обычные проверки и применимое решение владельца.

Понятный health-статус, структурированные логи и однозначно определяемая по идентификатору сборки версия обязательны и достаточны для локализации сбоя и отката ([`SYS_026`](system_specification.md#sys_026)). Формальный аудит решений и отдельный владельческий протокол на каждое обновление или откат становятся обязательными вместе с heartbeat/lease нескольких исполнителей ([`ARC_CMP_007`](#arc_cmp_007)), то есть при появлении более чем одного одновременного исполнителя.

Физическая топология, конкретное средство очереди и наблюдения, механизм развёртывания и поставщик принадлежат инфраструктуре и ADR.

## 4. Стабильные архитектурные потоки

<a id="arc_flow_001"></a>
### ARC_FLOW_001 — Обычная задача

- `traces_to`: [`SYS_001`](system_specification.md#sys_001), [`SYS_036`](system_specification.md#sys_036), [`SYS_003`](system_specification.md#sys_003), [`SYS_004`](system_specification.md#sys_004), [`SYS_023`](system_specification.md#sys_023)
- `implements`: [`ARC_CMP_001`](#arc_cmp_001), [`ARC_CMP_002`](#arc_cmp_002), [`ARC_CMP_003`](#arc_cmp_003), [`ARC_CMP_004`](#arc_cmp_004), [`ARC_CMP_006`](#arc_cmp_006), [`ARC_CMP_008`](#arc_cmp_008)

```text
ввод: цель / данные / известные критерии успеха
→ нормализация канала / критерии успеха / требуемые доказательства
→ входная безопасность: личность / квоты / тип / доверие / область / допустимость модели
→ правила владельца / подтверждение / аварийный выключатель
→ создание состояния и runtime_task_id
→ очередь либо немедленное выполнение
→ RuntimePort / отдельный Run выбранной среды
→ разрешённая проекция контекста
→ выбранная модель и необходимые возможности
→ единый формат результата
→ Quality Gate относительно критериев успеха и доказательств
→ один типизированный переход:
  - проверенный результат;
  - либо пересмотр плана: причина отклонения → новый Run в пределах лимита;
  - либо требуется выбор владельца:
    - подтвердить → проверенный результат;
    - скорректировать критерии или результат → новый Run;
    - остановить → контролируемый исход;
  - либо контролируемый исход
→ возврат через выбранный канал или уведомление
```

<a id="arc_flow_002"></a>
### ARC_FLOW_002 — Вызов инструмента или внешнее действие

- `traces_to`: [`SYS_020`](system_specification.md#sys_020), [`SYS_021`](system_specification.md#sys_021), [`SEC_CTL_007`](system_specification.md#sec_ctl_007), [`SEC_CTL_008`](system_specification.md#sec_ctl_008)
- `implements`: [`ARC_CMP_002`](#arc_cmp_002), [`ARC_CMP_003`](#arc_cmp_003), [`ARC_CMP_005`](#arc_cmp_005), [`ARC_CMP_007`](#arc_cmp_007)

```text
планируемая возможность
→ Skill / запрошенная Capability / минимальный набор Tools
→ before_tool / техническая авторизация
→ изолированная рабочая область при необходимости
→ повторная проверка значимых параметров или решение владельца
→ разрешённая реализация
→ after_tool / результат + событие + происхождение
```

Чувствительные параметры повторно проверяются перед внешним действием. Повтор выполнения не должен незаметно дублировать уже совершённое действие.

### ARC_FLOW_004 — Плановая задача
