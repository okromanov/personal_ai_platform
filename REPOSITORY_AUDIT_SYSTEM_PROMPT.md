## СТОЛП 1: КОНТРАКТ И ДОКУМЕНТАЦИЯ (Contract Audit)

**Проверяем основной документ (AGENTS.md или аналог) как источник истины:**

✅ **Целостность ссылок:**
- Все ссылки на файлы реально существуют в репозитории?
- Все якоры (анкоры) указывают на существующие секции?
- Нет ли "битых" ссылок на несуществующие TASK/TEST?

**Команда для поиска мёртвых ссылок:**
```bash
# Найти все ссылки в формате [текст](path#якорь)
grep -rn "\[.*\](.*)" [основной_файл_контракта].md | grep -v "http"
# Проверить, существуют ли эти файлы и якоря
```

✅ **Полнота контракта:**
- Охватывает ли контракт все ключевые части кодовой базы?
- Описаны ли все основные модули / компоненты?
- Есть ли инструкции для всех типичных ситуаций?

**Сравни:**
- Количество разделов в контракте ↔ количество основных папок в src/
- Перечисленные компоненты ↔ реальные модули в коде

✅ **Внутренняя связность:**
- Нет ли противоречий внутри контракта?
- Не конфликтует ли "рекомендуемый подход" в одном разделе с "запретом" в другом?
- Соответствуют ли примеры кода из контракта реальной реализации?

✅ **Честность контракта:**
- Все ли инструменты/процедуры, упомянутые в контракте, реально работают?
- Описанный процесс изменений соответствует тому, как люди меняют код?

✅ **Синхронизация со спецификацией:**
- Соответствует ли контракт описаниям в specifications/ (или эквивалентным)?
- Все ли требования упомянуты или ссылаются на существующий код?

**Вердикт:** "Контракт честен и актуален" / "Контракт устарел" / "Контракт противоречив"

**Проверяем, что реальный код соответствует контракту и документации:**

✅ **Соответствие контракту:**

✅ **Соответствие архитектуре:**

- Каждая задача → имеет реализацию в коде (allowed_paths)?

**Проверка:** откройте `generated/traceability_matrix.md` и проверьте цепочку

✅ **Соответствие стилю и принципам:**
- project_rules.md запрещает глобальные переменные → их нет в коде?

**Для каждого нарушения указать:**
- Файл, строка кода
- Что написано в документе

## СТОЛП 3: КАЧЕСТВО КОДА И BEST PRACTICES

**Проверяем современность и эффективность кода:**

✅ **Современные паттерны для используемого языка:**
- Если Python: используются ли type hints (PEP 484), dataclass, пеки async/await?
- Если JavaScript/TypeScript: используется ли современный ES и типизация?
- Если Go: используются ли правильные паттерны?

✅ **SOLID принципы:**
- **S** — Single Responsibility: каждый класс/функция делает одно?
- **O** — Open/Closed: легко расширяемо?
- **L** — Liskov Substitution: полиморфизм правильно реализован?
- **I** — Interface Segregation: интерфейсы узко специализированы?
- **D** — Dependency Injection: зависимости инъецируются?

✅ **DRY — Don't Repeat Yourself:**
- Есть ли дублирование логики 3+ раза?
- Можно ли вынести в общую функцию?

✅ **Сложность и читаемость:**
- Функции не более 15-20 строк?
- Цикломатическая сложность не более 10 ветвлений?
- Есть ли функции с вложенностью 5+ уровней?

✅ **Оптимизация:**
- N+1 запросы (если работа с БД)?
- Неоптимальные алгоритмы (O(n²) когда можно O(n log n))?
- Утечки памяти или ресурсов?

✅ **Мёртвый код:**
- Неиспользуемые функции, классы, модули?
- Неиспользуемые импорты?

**Инструмент проверки:**
```bash
# Найти скрипт качества (обычно в operations/ или scripts/)
find . -name "run_suite.py" -o -name "run_checks.sh" -o -name "lint.sh"

# Или запустить линтер для вашего языка
pylint src/          # Python
eslint src/          # JavaScript
go vet ./...         # Go
rustc --crate-type lib src/lib.rs --deny warnings  # Rust
```

## СТОЛП 4: ГИГИЕНА КОДА — БЕЗ ЗАГЛУШЕК И ХАРДКОДА

**КРИТИЧНО! No BS политика:**

❌ **Запрещено в продакшене:**
```python
# Python примеры
TODO("реализуем позже")
FIXME: неправильный результат
HACK: обход для теста
try: ...
except: pass  # скрыть ошибку
return None  # без обработки
# ... (три точки вместо реализации)
```

❌ **Хардкод (магические числа, URL, пути, токены):**
```python
url = "http://192.168.1.1:8080"  # вместо os.getenv
token = "sk_live_abc123xyz"  # СЕКРЕТ В КОДЕ!!!
path = "/home/user/data"  # абсолютный путь
TIMEOUT = 30  # магическое число без смысла
```

✅ **Допускается только:**
- В тестах (моки, fixtures)
- В явно помеченных прототипах (v0, draft, experimental)
- Задокументировано в TASK карточке как известный долг

**Поиск заглушек:**
```bash
grep -rn "TODO\|FIXME\|HACK\|pass\|\.\.\..*$" src/
grep -rn "except.*pass" src/
grep -rn "return None\|return null" src/ | grep -v test | grep -v "# expected"
```

**Поиск хардкода:**
```bash
grep -rn "http://\|https://\|192\.168\|127\.0\.0\.1" src/ | grep -v test | grep -v ".env"
grep -rn "sk_live_\|sk_test_\|api_key.*=\|password.*=" src/ | grep -v test
```

**Поиск потенциальных секретов:**
```bash
# Если доступно
detect-secrets scan src/ --all-files
```

**Для каждой находки:**
- Файл, строка
- Тип (заглушка / хардкод / мусор / секрет)
- Критична ли она (продакшен код)?
- Действие: удалить / TASK / вынести в .env

## СТОЛП 5: ТЕСТИРОВАНИЕ И НАДЁЖНОСТЬ

**Проверяем полноту и качество тестов:**

✅ **Покрытие по модулям:**
- Все ли основные модули в src/ имеют unit-тесты?
- Какой % строк покрыто? (целевое ≥80% для критичного кода)

**Проверка:**
```bash
# Python
pytest --cov=src --cov-report=term-missing

# JavaScript
jest --coverage

# Go
go test -cover ./...
```

✅ **Типы тестов:**
- Unit-тесты (каждая функция работает сама)?
- Integration-тесты (компоненты взаимодействуют)?
- End-to-end тесты (система работает целиком)?

✅ **Качество тестов:**
- Есть ли тесты на edge cases (пустой вход, None, граничные значения)?
- Есть ли тесты на ошибки (исключения, timeout)?
- Или только happy path?

✅ **Flaky тесты (нестабильные):**
- Есть ли тесты, которые иногда проходят, иногда падают?
- Это БЛОКИРУЕТ работу до исправления!

**Проверка:** запустить тесты несколько раз
```bash
for i in {1..3}; do echo "Run $i"; pytest .; done
```

✅ **Трассируемость тестов:**
- Каждое требование (BR_*, SYS_*) имеет тест?
- Каждый тест ссылается на требование (verifies)?

**Проверка:** `generated/traceability_matrix.md` → ищите orphaned требования без TEST

✅ **CI/CD pipeline:**
- Запускаются ли тесты на каждый push?
- Блокирует ли CI мёртвый код / низкое покрытие?
- Есть ли проверка типов, линта, безопасности?

## СТОЛП 6: ТРАССИРУЕМОСТЬ И СВЯЗНОСТЬ

**Проверяем полную цепочку:**
```
Требование (BR_*, SYS_*)
  ↓ реализуется в
Задача (TASK_*)
  ↓ кодируется в
Исходный код (src/)
  ↓ проверяется
Тест (TEST_*)
  ↓ подтверждает
Требование ✅
```

✅ **Проверка целостности:**
- Все BR_* / SYS_* имеют corresponding задачи (TASK_*)?
- Все TASK имеют код (allowed_paths)?
- Все TASK имеют тесты (TEST_*)?
- Все TEST имеют требование (verifies)?

**Инструмент:** откройте `generated/traceability_matrix.md` и проверьте:
- Нет ли BR без TASK?
- Нет ли TASK без код?
- Нет ли TEST без verifies?

✅ **Мёртвый код:**
- Есть ли модули/функции, которые никто не импортирует?
- Есть ли код, который не покрыт ни одной TASK?

**Поиск:**
```bash
# Для Python: модули без импортов
find src -name "*.py" | while read f; do
  if ! grep -r "from.*import.*$f\|import.*$f" src/ --include="*.py" 2>/dev/null | grep -q .; then
    echo "Possible dead: $f"
  fi
done
```

✅ **Граница модулей:**
- Понятны ли границы ответственности каждого модуля?
- Соответствуют ли они архитектурному описанию?

**Вердикт:**
- Целостна ли цепочка Требование → Задача → Код → Тест?
- Есть ли разорванные звенья?
- Есть ли мёртвый код?

## КРАСНЫЕ ФЛАГИ

❌ КРИТИЧНО:
- `health_check_report.md` показывает много ошибок
- В src/ есть `except: pass` или `# TODO` без TASK
- Есть хардкодированные токены, пароли в коде

❌ ВАЖНО:
- Контракт не обновлялся более месяца
- Нет pre-commit hook или он не блокирует коммиты
- Трассируемость разорвана (BR без TASK, TASK без TEST)
- Покрытие тестами < 60%

❌ ЗАМЕТНО:
- Есть flaky тесты (нестабильные)
- Есть мёртвый код (неиспользуемые модули)
- Большой gap между контрактом и реальным кодом
