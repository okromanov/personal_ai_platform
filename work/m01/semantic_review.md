# m01 — Процедура смысловой проверки

## 1. Назначение

Этот файл не дублирует схему результа. Единственные правила, уровни замечаний и JSON-схема заданы в [`operations/semantic_review.md`](../../operations/semantic_review.md#обязательная-смысловая-проверка-при-принятии-этапа). Здесь зафиксирован только m01-маршрут.

## 2. Предусловия

1. Все обязательные GitHub Actions успешны на одном опубликованном SHA.
2. Evidence bundle для этого SHA подтверждает `TEST_001` и `TEST_002`.
3. Проверку выполняет новый сеанс без истории разработки либо отдельный проверяющий.

Аудит в том же контексте считается предварительным и не может создать формальный `pass`.

## 3. Область m01

Проверяющий читает точную редакцию как незнакомый проект и охватывает:

- все девять ADR: `ADR_001`–`ADR_004` как базовые решения m01, `ADR_005`–`ADR_009` как кандидаты, которые m01 не имеет права преждевременно принять;
- иерархию BR/SYS/THR/SEC/ARC/INF, трассировку, milestones, TASK, TEST и evidence;
- основной экран владельца, инструкцию агента, CI и полный путь принятия;
- пять стратегических вопросов из канонической процедуры.

## 4. Результат

Каноническая запись сохраняется как `runtime/evidence/m01_semantic_review.json` и проверяется `operations/scripts/acceptance/apply.py`. Запись со старым SHA, иным набором полей, `remarks` вместо `pass` или с неразрешённым `critical`/`high` не открывает переход принятия.

Для m01 в записи дополнительно требуются точная команда `ПОДТВЕРЖДАЮ СОСТАВ V1`, вычисленный из `priority: core` точный список ID и непустые `strategic_answers` с пятью ключами из канонической схемы. Фраза в свободной форме не подменяет это формальное действие.

## 5. Следующее действие

После успешной свежей проверки и формального подтверждения периметра владелец получает один выбор: `ПРИНИМАЮ m01` или `ВОЗВРАЩАЮ m01: <причина>`.
