### AUD-034 — Канонический gate красный на HEAD: Bandit B314 в diagram_lint.py

- **Severity/Confidence/Evidence state:** high / high / CONFIRMED
- **Baseline:** introduced-by-change
- **Файл:** [`diagram_lint.py:171`](../../operations/scripts/documents/diagram_lint.py)
- **Ожидаемый контракт:** [`AGENTS.md`](../../AGENTS.md) §3 — «Слияние или принятие этапа запрещено, пока общий gate не подтверждён для точного SHA»; `run_suite.py full` обязан завершаться с exit 0 на коммитах, допущенных к слиянию.
- **Наблюдаемое поведение:** `run_suite.py full` завершается с exit 1 на третьем шаге. `_check_structure()` вызывает `xml.etree.ElementTree.fromstring()` для содержимого SVG-файла; bandit 1.7.5 (pinned, та же версия, что в CI) выдаёт B314 severity MEDIUM, а шаг запускается с `--severity-level medium`, то есть находка блокирующая. Результат воспроизведён дважды подряд, ровно один result в JSON. Остальные 14 шагов gate при отдельном запуске проходят. Файл добавлен 2026-08-31 коммитом `957a434`, то есть уже после предыдущего аудита (baseline 2026-08-30); за это время в `main` приняты PR #94 и #95. В репозитории нет ни одного `# nosec`, а `defusedxml` не объявлен прямой зависимостью в [`requirements_dev.in`](../../operations/quality/requirements_dev.in) — он присутствует только транзитивно.
- **Воздействие и достижимость:** gate не проходит на текущем SHA, то есть по собственному правилу репозитория этот SHA не был допустим к слиянию. Достижимость максимальная — падение детерминированное, на каждом запуске. Реальная эксплуатируемость самого B314 низкая (разбираются файлы схем из самого репозитория), но severity здесь определяет не XML-риск, а нарушение обязательного gate.
- **Как воспроизвести:** `python3.12 -m venv .venv && .venv/bin/pip install --require-hashes -r operations/quality/requirements_dev.txt && .venv/bin/python operations/scripts/quality/run_suite.py full` на SHA `2e69176`; либо изолированно `.venv/bin/python -m bandit -r operations/scripts src --severity-level medium -f json -q`.
- **Почему предыдущий аудит пропустил:** находка не существовала на 2026-08-30 — [`diagram_lint.py`](../../operations/scripts/documents/diagram_lint.py) появился 2026-08-31. Пропустил не аудит, а отсутствующий серверный gate ([`AUD-007`](audit_register.md#aud-007)).
- **Рекомендованное исправление:** решение владельца между двумя честными вариантами. (1) Объявить `defusedxml` прямой зависимостью и разбирать SVG через `defusedxml.ElementTree` — устраняет причину. (2) Если разбор строго ограничен файлами самого репозитория и это осознанное решение — зафиксировать его явно в коде и в коммите. Подавление ради зелёного результата без одного из этих двух обоснований запрещено [`AGENTS.md`](../../AGENTS.md) §5.1.
- **Как проверить исправление:** `run_suite.py full` доходит до конца с exit 0 на новом SHA; шаг `Security audit (Bandit)` не содержит результатов severity ≥ medium.
- **Критерий закрытия:** зелёный `Project check` на точном SHA.

### AUD-035 — Секрет-скан CI не покрывает git-историю

- **Severity/Confidence/Evidence state:** medium / high / CONFIRMED
- **Baseline:** pre-existing
- **Файл:** [`project_check.yml`](../../.github/workflows/project_check.yml), шаг «Scan dependencies and secrets»
- **Ожидаемый контракт:** секрет, удалённый из рабочего дерева, остаётся в git-истории и должен обнаруживаться; репозиторий планирует работать с реальным токеном Telegram и ключами провайдера модели ([`SEC_CTL_005`](../../specifications/system_specification.md#sec_ctl_005), [`ADR_009`](../../adr/adr_009_secret_management_strategy.md)).
- **Наблюдаемое поведение:** CI выполняет `gitleaks dir . --redact`, то есть сканирует только рабочее дерево на проверяемом SHA. Режим `gitleaks git`, разбирающий коммиты, не запускается никогда. Запуск `gitleaks git .` тем же pinned бинарём 8.30.1 по полной истории (467 коммитов после `--unshallow`) даёт 4 срабатывания правила `generic-api-key`, которых сканирование рабочего дерева не видит: они находятся в удалённых с тех пор файлах `AUDIT_FRAMEWORK.md` и `REPOSITORY_AUDIT_SYSTEM_PROMPT.md` (коммиты от 2026-08-25). Все четыре проверены по содержимому и являются **иллюстративными примерами** в блоке «❌ ПЛОХО (хардкод)» — реального секрета в истории не найдено, stop-условие раздела 3.5 не наступило. Дефект не в этих четырёх строках, а в том, что контроль структурно не способен увидеть этот класс.
- **Воздействие и достижимость:** любой секрет, случайно закоммиченный и удалённый следующим коммитом, проходит CI зелёным навсегда. Достижимость высокая: репозиторий ведётся агентами, а [`TASK_013`](../tasks/task_013_inf_008.md)/[`TASK_016`](../tasks/task_016_real_telegram.md) вводят реальные токены и файлы `.env` в рабочий контур.
- **Как воспроизвести:** `gitleaks dir . --no-banner` (0 находок) против `gitleaks git . --no-banner` (4 находки) на полной истории. При shallow-клоне второй режим тоже слеп — сначала нужен `git fetch --unshallow`.
- **Рекомендованное исправление:** добавить в шаг сканирования второй прогон `gitleaks git`, а в job — раскрытие истории (шаг `--unshallow` в этом workflow уже есть в соседнем job и может быть переиспользован). Четыре известных срабатывания-примера оформить через `.gitleaksignore` по fingerprint, а не ослаблением правила.
- **Как проверить исправление:** намеренно закоммитить и следующим коммитом удалить синтетический высокоэнтропийный токен в тестовой ветке — `Project check` обязан упасть.

### AUD-036 — Строка «Состояние gate/CI» в статусе владельца не отражает состояние gate

- **Severity/Confidence/Evidence state:** medium / high / CONFIRMED
- **Baseline:** pre-existing
- **Файл:** [`human_status.py`](../../operations/scripts/status/human_status.py) (`_audit_status()`), [`project_status.md`](../../project_status.md)
- **Ожидаемый контракт:** рекомендация [`AUD-010`](audit_register.md#aud-010) — «добавить в генератор статуса поле состояния gate/CI (или явную пометку „последняя проверка недоступна“)», чтобы владелец, читающий только [`project_status.md`](../../project_status.md), видел, что gate красный.
- **Наблюдаемое поведение:** строка добавлена и называется «Состояние gate/CI», но её значение вычисляется исключительно из числа незакрытых критических строк реестра: сейчас «ЕСТЬ незакрытые критические замечания (1)». Ни одного входа от фактического прогона gate или CI у генератора нет. На проверяемом SHA канонический gate реально красный ([`AUD-034`](#aud-034)), и в [`project_status.md`](../../project_status.md) об этом нет ничего. Обратная асимметрия так же реальна: после закрытия [`AUD-007`](audit_register.md#aud-007) эта строка станет успокаивающей независимо от того, проходит gate или нет.
- **Воздействие и достижимость:** заголовок обещает владельцу состояние gate/CI, а показывает производную от реестра — то есть даёт правдоподобный, но не соответствующий источнику сигнал. Это тот самый класс, против которого написана [`AUD-010`](audit_register.md#aud-010); её remediation закрыла видимость критических находок, но не видимость gate.
- **Как воспроизвести:** сравнить exit code `run_suite.py full` на SHA `2e69176` (1, падение на Bandit) с содержимым строки «Состояние gate/CI» в [`project_status.md`](../../project_status.md) того же SHA.
- **Рекомендованное исправление:** либо переименовать строку в то, чем она является («Незакрытые критические замечания аудита»), и добавить отдельную строку состояния gate с явным «последняя проверка недоступна», когда SHA-bound evidence нет; либо связать значение с `runtime/evidence/quality_suite.json` и его SHA. Первый вариант дешевле и честнее до восстановления CI.
- **Как проверить исправление:** на SHA с красным gate [`project_status.md`](../../project_status.md) либо показывает красное состояние gate, либо явно сообщает, что проверка недоступна, и не называет строку состоянием gate.

### AUD-037 — Review date в реестре разбирается, но ничем не обеспечена

- **Severity/Confidence/Evidence state:** low / high / CONFIRMED
- **Baseline:** pre-existing
- **Файл:** [`run_suite.py`](../../operations/scripts/quality/run_suite.py) (`validate_audit_baseline()`)
- **Ожидаемый контракт:** §2 и §5 [`audit_register.md`](audit_register.md) вводят обязательную дату пересмотра для каждой незакрытой находки и для каждого `accepted_risk`; дата, которую никто не проверяет, контролем не является ([`AGENTS.md`](../../AGENTS.md) §5.1 о проверках, неспособных провалиться).
- **Наблюдаемое поведение:** `AUDIT_ROW` захватывает `review_date`, но единственная проверка — что поле не равно `—` для нестатуса `resolved`. Сравнения с текущей датой нет нигде: ни в gate, ни в `check.py`, ни в генераторе статуса. На дату этого аудита строки `AUD-001`…`AUD-006` имеют review date `2026-09-02`, то есть срок наступил сегодня, и ни одна проверка на это не реагирует. Owner dashboard показывает «Ближайшая дата проверки», то есть владелец информирован, но автоматического сигнала о просрочке не существует.
- **Воздействие и достижимость:** находки и принятые риски бесшумно стареют мимо собственного срока пересмотра. Достижимость гарантированная — наступает по календарю.
- **Как воспроизвести:** прочитать `validate_audit_baseline()` — `review_date` после разбора не используется; выполнить `run_suite.py full` на дату после 2026-09-02: шаг валидации конфигурации проходит.
- **Рекомендованное исправление:** сравнивать `review_date` с текущей датой и выдавать явный отказ либо предупреждение для просроченных строк. Решение о том, блокирует ли просрочка gate или только громко показывается владельцу, — за владельцем: первое строже, второе не превращает календарь в блокер поставки.
- **Как проверить исправление:** negative test с фиксированной «сегодняшней» датой и строкой с прошедшим `review_date` обязан провалить проверку.

### AUD-038 — Реестр совмещает машинно-читаемую таблицу состояния и неограниченно растущий архив карточек

- **Severity/Confidence/Evidence state:** low / high / CONFIRMED
- **Baseline:** pre-existing
- **Файл:** [`audit_register.md`](audit_register.md)

### AUD-039 — TASK_016 не требует подлинности входящего Telegram-канала

- **Severity/Confidence/Evidence state:** medium / high / CONFIRMED
- **Baseline:** pre-existing
- **Файл:** [`task_016_real_telegram.md`](../tasks/task_016_real_telegram.md) §4, §5, §7, §8
- **Ожидаемый контракт:** [`SEC_CTL_001`](../../specifications/system_specification.md#sec_ctl_001) («Проверка личности до выполнения задачи») входит в состав [`m02`](../../milestones.md#m02), то есть является обязательным для этого этапа, а не отложенным. Раздел 7.4 применённого prompt требует отдельно проверять подлинность входящего канала — подпись/секрет webhook, защиту от подмены владельца на канальном уровне — отдельно от authentication внутри приложения.
- **Наблюдаемое поведение:** весь owner-control контур ключуется на `subject_id`, который [`Orchestrator.handle()`](../../src/orchestration/orchestrator.py) получает от вызывающего кода, а тот извлекает его из метаданных сообщения (`telegram_user_id` в [`TelegramChannel.inject_message()`](../../src/channels/telegram.py)). `verify_identity()` сравнивает эту строку с идентификатором владельца — то есть доверяет полю, пришедшему из внешнего сообщения. [`TASK_016`](../tasks/task_016_real_telegram.md) вводит реальный Bot API и в §4 п.1 допускает webhook, но ни план (§5), ни проверки (§7), ни критерии готовности (§8) не содержат ни одного пункта о секретном токене webhook (`X-Telegram-Bot-Api-Secret-Token`), IP-allowlist Telegram или ином подтверждении, что update действительно пришёл от Telegram. §7 требует только «отсутствие вызова модели для чужого user_id» — это проверка отказа для *другого* идентификатора, а не защита от подделки *владельческого*. `allowlist` в §5 относится к [`NetworkPolicy`](../../src/operations/network_policy.py), то есть к egress, и к подлинности ingress отношения не имеет.
- **Воздействие и достижимость:** если [`TASK_016`](../tasks/task_016_real_telegram.md) будет выполнена по написанному в режиме webhook, любой, кто узнает URL endpoint, сможет отправить update с `telegram_user_id` владельца и пройти [`SEC_CTL_001`](../../specifications/system_specification.md#sec_ctl_001), аварийный выключатель при этом остаётся единственным барьером. Сегодня код не развёрнут и уязвимости не существует — поэтому medium, а не high: дефект находится в карточке планируемой работы, и стоимость его устранения сейчас минимальна.
- **Как воспроизвести:** `grep -in "webhook\|подпис\|secret.token\|spoof" work/tasks/task_016_real_telegram.md` — единственное совпадение относится к выбору webhook/polling и к получению токена бота через `SecretProvider`, ни одного пункта о подлинности входящего запроса.
- **Рекомендованное исправление:** дополнить [`TASK_016`](../tasks/task_016_real_telegram.md) явным пунктом плана и критерием готовности: при webhook — обязательный secret token и его проверка на каждом update, при polling — фиксация того, что подлинность обеспечивается исходящим соединением к Telegram; и отрицательный TEST «поддельный update с идентификатором владельца отклонён». Изменение карточки — работа владельца/агента по обычному процессу, аудитор её не вносит.
- **Как проверить исправление:** в [`TASK_016`](../tasks/task_016_real_telegram.md) §8 присутствует критерий подлинности канала, а связанный TEST содержит отрицательный сценарий подделки идентификатора владельца.

## 6. Данные и приватность

- **Инвентарь данных.** `task_messages.user_input` — текст сообщения владельца, `task_messages.metadata_json` — `telegram_user_id`/`telegram_chat_id`; оба в SQLite ([`sqlite_store.py`](../../src/task_state/sqlite_store.py)). `observation_events` ([`sqlite_store.py`](../../src/observability/sqlite_store.py)) — только числа и булевы значения. `owner_control_actions.json` — дескрипторы чувствительных действий.
- **Egress.** Нулевой: `CURRENT_NETWORK_POLICY = NetworkPolicy()` — пустой allowlist, ни ingress, ни egress не разрешены; модель — детерминированная заглушка без сети. Отправка данных внешнему провайдеру появится только с [`TASK_015`](../tasks/task_015_real_model_provider.md).
- **Минимизация.** Подтверждённая сильная сторона: [`ObservabilityCollector`](../../src/observability/collector.py) конструктивно не может записать свободный текст — `measurements` принимает только `int`/`float`/`bool`, а `record_technical_event()` принимает числовой код вместо сообщения об ошибке. Это не соглашение в комментарии, а проверяемый контракт с `TypeError`.
- **Retention и удаление.** Не заданы и не реализованы: у [`TaskLifecycleStore`](../../src/task_state/base.py) нет метода удаления, TTL отсутствует. Отложено осознанно — [`SYS_011`](../../specifications/system_specification.md#sys_011), [`SYS_012`](../../specifications/system_specification.md#sys_012), [`SEC_CTL_019`](../../specifications/system_specification.md#sec_ctl_019) отнесены к [`m04`](../../milestones.md#m04), а полное резервное копирование и восстановление — к [`m04`](../../milestones.md#m04)/[`m06`](../../milestones.md#m06), причём [`milestones.md`](../../milestones.md) явно запрещает подменять это облегчённым smoke-тестом на [`m02`](../../milestones.md#m02). Находкой не оформлено. Наблюдение для планирования: сообщения владельца начинают накапливаться уже с [`m02`](../../milestones.md#m02), а средства их просмотра и удаления появляются только на [`m04`](../../milestones.md#m04) — к этому моменту существующий объём данных окажется без определённого жизненного цикла. Отдельно: множества `authorized_action_ids` и `executed_actions` служат защитой от повторного выполнения и не имеют правила усечения, то есть растут монотонно.
- **PII в engineering artifacts.** Не обнаружено: `gitleaks dir` чист, реальных персональных данных в fixtures нет, во всех тестах используются синтетические идентификаторы вида `test_user`.
- **Evidence state:** `CONFIRMED` для инвентаря, egress и минимизации; `NOT_CHECKED` для retention как контроля — он относится к будущему этапу.
