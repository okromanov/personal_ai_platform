#### Требования, задачи и поставка

Нормативные SYS/SEC/ARC/INF требования разделены, TASK содержит `work_state`, `allowed_paths`, `implements`, TEST и критерии сдачи. `allowed_paths` определяет допустимый scope изменения, не доказательство выполнения. `m02` содержит 12 завершённых задач, `TASK_013` в работе, а реальные runtime/model/Telegram и живой e2e — последующие TASK_014–017; UI, полная память и внешние интеграции — следующие этапы.

Наиболее частый уровень после своих мутирующих операций повторяет fast, но не full. Отдельного подтверждённого deploy/rollback шага и restore drill для m02 ещё нет. ## 4. Карточки findings

<a id="aud-045"></a>
### AUD-045 — READ без явного списка ресурсов разрешает произвольный ресурс

- **Severity/Confidence/Evidence state:** MEDIUM / HIGH / CONFIRMED.
- **Baseline:** pre-existing; тот же условный guard присутствует на предыдущем проверенном SHA `3006ad603e57d9acc3bb3cd50455c04223904d14`; в AUD-001–044 причина не зарегистрирована.
- **Файл:** [`src/tools/registry.py`](../../src/tools/registry.py), строки 41–45 и 118–125; [`TEST_011`](../tests/test_011.md).
- **Ожидаемый контракт:** SEC_CTL_003/006/007 и TASK_005 требуют минимальных полномочий и явно разрешённой области ресурсов для вызова инструмента, в том числе для чтения.
- **Наблюдаемое поведение:** `Capability.__post_init__` требует непустой `allowed_resources` лишь для классов, отличных от READ. Проверка `tool_call.resource` вызывается лишь если этот список непуст. Значит пустой список у READ работает как неявный wildcard.
- **Как воспроизвести:** на исходниках с подтверждёнными Git blob SHA зарегистрировать `Capability('read_file', READ, handler, {'owner'})` без ресурсов и вызвать `ToolCall(resource='secret.txt')`. Наблюдение: `result.succeeded=true`, handler вызван с `secret.txt`. Машинная запись — [`negative_probe.json`](evidence/2026_09_23_completion/negative_probe.json).
- **Воздействие и достижимость:** после подключения реального read-handler, использующего поле `resource`, эталонный шлюз пропустит запрос за пределы ожидаемой области; сейчас нет подключённого реального обработчика и не доказана фактическая утечка. Поэтому MEDIUM.
- **Почему предыдущий аудит пропустил:** тест позитивного READ-сценария создаёт capability с пустым списком, а отрицательный сценарий проверяет только непустой allowlist; не было пробы «пустой список + запрещённый ресурс».
- **Рекомендованное исправление:** требовать явный список ресурсов и для READ; если нужен wildcard, выделить проверяемую отдельную декларацию и ограничить область. Не менять policy без проверки ожидаемых случаев использования.
- **Как проверить исправление:** пустой список отвергается при регистрации или вызове до handler; разрешённый ресурс проходит; отрицательный тест должен падать на текущей реализации и проходить после исправления, полный Project check зелёный на новом SHA.
- **Критерий закрытия:** поведенческий тест и серверный полный gate на одном точном SHA, ссылка на evidence в реестре.
