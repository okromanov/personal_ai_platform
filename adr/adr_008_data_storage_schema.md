# ADR_008 — Выбор схемы хранилища данных

## 1. Назначение

Зафиксировать PostgreSQL как кандидата для проверки хранения данных, не принимая схему до нагрузочного и recovery evidence.

## 2. Контекст

V1 требует управление несколькими типами данных:

1. **Долговременная память** ([`BR_022`](../specifications/business_requirements.md#br_022)): семантические встраивания + текст
2. **История контекста** ([`BR_023`](../specifications/business_requirements.md#br_023)): управляемый архив переписки
3. **Проектный контекст** ([`SYS_012`](../specifications/system_specification.md#sys_012)): решения, обязательства, риски и следующие действия — сущности связаны между собой (проект ↔ задача ↔ решение ↔ риск ↔ следующее действие), поэтому это не плоская запись, а граф связей; требует представления, пригодного для обхода связей, а не только точечного чтения по ключу
4. **Области данных** ([`BR_024`](../specifications/business_requirements.md#br_024), [`SYS_029`](../specifications/system_specification.md#sys_029), [`SEC_CTL_006`](../specifications/system_specification.md#sec_ctl_006)): рабочий и личный контекст
5. **Жизненный цикл памяти** ([`SEC_CTL_019`](../specifications/system_specification.md#sec_ctl_019)): исправление и удаление без возврата старой записи

Требования:
- **Структурированность:** Задачи и события имеют чёткую схему
- **Масштабируемость:** От КБ памяти до ГБ архива истории
- **Поиск:** По памяти нужен семантический поиск (embedding vector); ключевой риск — не объём хранения, а точность поиска по мере роста архива: чистый top-K по косинусному сходству эмбеддинга неизбежно теряет точность, когда в индексе накапливаются тысячи похожих, устаревших или уже опровергнутых записей — нужна стратегия, поддерживающая точность поиска на растущем архиве, а не только сам факт наличия векторного индекса
- **Изоляция:** Разные области данных ([`BR_024`](../specifications/business_requirements.md#br_024), [`SEC_CTL_006`](../specifications/system_specification.md#sec_ctl_006))
- **Аудит:** Кто и когда изменил что (для [`SEC_CTL_019`](../specifications/system_specification.md#sec_ctl_019))

## 3. Предлагаемое решение

В [`m04`](../milestones.md#m04) проверить **PostgreSQL** как кандидата на основное хранилище структурированных данных:

1. **Таблицы основные:**
   - `agent_memory` — встраивания (embeddings) + источник текста ([`BR_022`](../specifications/business_requirements.md#br_022))
   - `context_history` — архив контекстов по SHA версии ([`BR_023`](../specifications/business_requirements.md#br_023))
   - `projects` — проектный контекст ([`SYS_012`](../specifications/system_specification.md#sys_012)); связи между сущностями (проект/задача/решение/риск/следующее действие) — отдельный структурный элемент этого типа памяти, а не факт в пользу другой СУБД: реализуется таблицами связей поверх выбранной СУБД либо графовым расширением (например, Apache AGE для PostgreSQL), решается отдельно от выбора основной СУБД в §4
   - `memory_corrections` — исправления и tombstone удаления ([`SEC_CTL_019`](../specifications/system_specification.md#sec_ctl_019))
   - `audit_log` — кто изменил что и когда ([`SEC_CTL_019`](../specifications/system_specification.md#sec_ctl_019))

2. **Индексы для производительности:**
   - BTREE индекс на `created_at` для быстрой фильтрации по времени
   - GiST/IVFFLAT индекс на `embedding` вектор для семантического поиска ([`BR_022`](../specifications/business_requirements.md#br_022))
   - UNIQUE индекс на `context_hash` для дедупликации ([`BR_023`](../specifications/business_requirements.md#br_023))

2.1. **Удержание точности поиска при росте архива** (см. риск в §2 «Поиск»): чистый ранжир по косинусному сходству не масштабируется как единственный сигнал — предлагается сочетать несколько сигналов при выборке кандидатов из `agent_memory`:
   - сходство эмбеддинга как первичный фильтр (уже покрыто индексом выше);
   - `confidence`/`created_at` как модификаторы ранжирования — недавняя или более уверенная запись предпочитается более старой/менее уверенной при близком сходстве;
   - явные связи из графа проектного контекста (пункт 3 ниже) как дополнительный сигнал релевантности для запросов, привязанных к конкретному проекту/задаче, а не только к тексту;
   - периодическая консолидация: записи, которые актуальный `memory_corrections` пометил исправленными/устаревшими, либо явные близкие дубликаты одного факта, схлопываются в одну актуальную запись с сохранением происхождения предыдущих версий в архиве, а не остаются висеть в индексе как равноправные кандидаты навсегда. Это снижает засорение top-K уже неактуальными совпадениями — то есть решает проблему точности поиска, а не только объёма хранения.
   Конкретный алгоритм ранжирования и правило консолидации подбираются на реальных данных в [`m04`](../milestones.md#m04), а не фиксируются здесь заранее.

3. **Шифрование:**
   - Шифрование at-rest средствами выбранной площадки
   - TLS для транспорта
   - Чувствительные поля шифруются ключом из выбранного хранилища секретов ([`ADR_009`](adr_009_secret_management_strategy.md#adr_009))

4. **Разделение прав:**
   - Применение row-level security (RLS) policies для изоляции областей ([`SEC_CTL_006`](../specifications/system_specification.md#sec_ctl_006))
   - Отдельные роли: agent (read/write), auditor (read-only), admin.

Конкретная СУБД, управляемый сервис и окончательная схема принимаются после сравнения с более простым вариантом и проверки backup/restore. Ссылки на RDS являются вариантом реализации только при принятии [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007).

## 4. Альтернативы

| Вариант | Преимущества | Недостатки |
|---------|-------------|-----------|
| **PostgreSQL (кандидат)** | Структура, зрелость, семантический поиск | Нужно проектировать и сопровождать схему |
| MongoDB | Гибкая схема, масштабируется горизонтально | JSON без типов усложняет валидацию, нет RLS |
| DynamoDB | Serverless, масштабируется, платишь за запросы | Дороже для частых запросов, менее гибкий поиск |
| SQLite | Простой, встроенный в Python | Не масштабируется, сложно делить между процессами |
| Ни СУБД (файлы) | Максимально просто | Нет поиска, нет изоляции, нет аудита |

Граф связей проектного контекста ([`SYS_012`](../specifications/system_specification.md#sys_012)) не входит в эту таблицу: это не альтернатива основной СУБД, а дополнительный структурный элемент, нужный только для одного типа памяти из пяти в §2 (проектный контекст), тогда как долговременная память ([`BR_022`](../specifications/business_requirements.md#br_022)) остаётся embedding-поиском, а не графом. Способ реализации связей (таблицы-связки поверх выбранной СУБД, графовое расширение вроде Apache AGE, либо отдельное графовое хранилище) сравнивается при декомпозиции [`m04`](../milestones.md#m04) вместе с основной СУБД, а не решается этим ADR заранее.

## 5. Последствия

**Положительные:**
- Структурированные данные с чёткой схемой
- Семантический поиск для памяти (встраивание + индекс)
- Изоляция данных через RLS ([`SEC_CTL_006`](../specifications/system_specification.md#sec_ctl_006))
- Полный аудит изменений ([`SEC_CTL_019`](../specifications/system_specification.md#sec_ctl_019))
- Резервное копирование и восстановление проверяются по [`INF_REQ_009`](../specifications/infrastructure_baseline.md#inf_req_009)

**Отрицательные:**
- Нужно спроектировать и проверить схему
- PostgreSQL требует больше ресурсов чем SQLite
- Нужна миграционная стратегия при изменении схемы ([`m03`](../milestones.md#m03)+)
- Без сочетания сигналов ранжирования и консолидации (§3 п. 2.1) точность семантического поиска будет деградировать по мере роста архива — чистый векторный индекс сам по себе не решает эту проблему на масштабе, только даёт техническую возможность поиска

## 6. Проверка

- [ ] PostgreSQL сравнивается минимум с одним более простым вариантом на целевом сценарии.
- [ ] Способ представления связей проектного контекста ([`SYS_012`](../specifications/system_specification.md#sys_012)) явно выбран (таблицы-связки / графовое расширение / отдельное графовое хранилище) и обоснован отдельно от выбора основной СУБД.
- [ ] Схема создаётся и обновляется воспроизводимыми миграциями.
- [ ] Проверены поиск, изоляция и аудит.
- [ ] Точность поиска (не только факт его наличия) измерена на синтетически состаренном архиве — с накопленными дубликатами, устаревшими и исправленными записями — и сравнена до/после применения ранжирования и консолидации из §3 п. 2.1.
- [ ] Консолидация не теряет факты, важные по [`BR_022`](../specifications/business_requirements.md#br_022): исходные версии остаются восстановимыми из архива происхождения, а не удаляются безвозвратно при схлопывании.
- [ ] Выполнен backup → restore → validation.
- [ ] Evidence и решение владельца зафиксированы до смены `decision_state`.
