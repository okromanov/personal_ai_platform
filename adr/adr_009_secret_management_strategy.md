# ADR_009 — Стратегия управления секретами и ключами

## 1. Назначение

Зафиксировать AWS Secrets Manager как кандидата для проверки управления секретами в m02.

## 2. Контекст

Приложение использует несколько типов секретов:

1. **API ключи:**
   - API-ключ выбранного поставщика модели (кандидат описан в ADR_005)
   - Telegram bot token (BR_006)
   - Внешние интеграции (BR_011, BR_020)

2. **Учётные данные доступа:**
   - Учётные данные выбранного хранилища данных (кандидат описан в ADR_008)
   - Учётные данные выбранной площадки (кандидат описан в ADR_007)
   - SSH ключи для серверов

3. **Шифровальные ключи:**
   - ключи, которые должны оставаться вне кода и журналов ([`SEC_CTL_005`](../specifications/system_specification.md#sec_ctl_005), [`INF_REQ_006`](../specifications/infrastructure_baseline.md#inf_req_006))
   - версии ключей, необходимые для контролируемой ротации без скрытой потери доступа

Требования ([`SEC_CTL_005`](../specifications/system_specification.md#sec_ctl_005), [`INF_REQ_006`](../specifications/infrastructure_baseline.md#inf_req_006)):
- Секреты не должны быть в коде или конфигах (git)
- Должна быть возможность ротации без перезагрузки
- Надо контролировать кто получает доступ к чему
- Должна быть возможность аудита (кто достал какой секрет когда)

## 3. Предлагаемое решение

Включить **AWS Secrets Manager** в сравнение способов управления секретами:

1. **Хранение:**
   - Каждый секрет хранится в AWS Secrets Manager
   - Шифрование at-rest через AWS KMS (автоматическое)
   - Версионирование для отката при необходимости

2. **Доступ из приложения:**
   - Python приложение использует boto3 для получения секретов
   - Кэширование секретов в памяти на время TTL (5 минут)
   - Автоматическая ротация при изменении в Secrets Manager

3. **Ротация:**
   - Период и способ ротации задаются политикой владельца и проверяются evidence
   - Ротация не требует перезагрузки приложения
   - Старый и новый ключ работают параллельно во время ротации

4. **Аудит и контроль:**
   - AWS CloudTrail логирует все обращения к секретам
   - IAM политики ограничивают кто может получить какой секрет
   - Алерты при подозрительном доступе.

Средство управления секретами принимается только после выбора площадки и проверки минимум одной альтернативы. До принятия ADR_007 AWS Secrets Manager не является обязательным.

## 4. Альтернативы

| Вариант | Преимущества | Недостатки |
|---------|-------------|-----------|
| **AWS Secrets Manager (кандидат)** | Интеграция с AWS, контроль и аудит | Дополнительная стоимость и привязка к AWS |
| HashiCorp Vault | Универсален, сильный аудит, ротация | Нужно развёртывать и поддерживать самому |
| Azure Key Vault | Интеграция с Azure | Применим только при выборе Azure |
| Переменные окружения | Просто на старте | Видны в PS, истории, не ротируются |
| Файлы в .gitignore | Самый простой | Очень опасно (видны на диске, в backup) |

## 5. Последствия

**Положительные:**
- Секреты не в коде ([`SEC_CTL_005`](../specifications/system_specification.md#sec_ctl_005), [`INF_REQ_006`](../specifications/infrastructure_baseline.md#inf_req_006))
- Ротация проверяется без ошибочной подмены контролем развёртывания
- Аудит кто доставал что (для compliance)
- Изоляция доступа через IAM политики
- Интеграция с AWS при принятии ADR_007

**Отрицательные:**
- Дополнительная стоимость ($5-10/месяц за 10-20 секретов)
- Зависимость от AWS Secrets Manager при выборе этого кандидата
- Нужно настроить IAM политики правильно

## 6. Проверка

- [ ] AWS Secrets Manager и минимум одна альтернатива проверены по единой scorecard.
- [ ] Секреты отсутствуют в коде, конфигурации, логах и traceback.
- [ ] Проверены least privilege, аудит, ротация и отказ доступа.
- [ ] Стоимость и vendor lock-in явно сопоставлены.
- [ ] Evidence и решение владельца зафиксированы до смены `decision_state`.
