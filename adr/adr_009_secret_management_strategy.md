# ADR_009 — Стратегия управления секретами и ключами

## 1. Назначение

Зафиксировать **`.env`-файл с ограниченными правами доступа на сервере** как выбранный подход к управлению runtime-секретами для проверки в [`m02`](../milestones.md#m02), с уже согласованным путём развития — SOPS+age как следующий шаг, если понадобится версионируемая история изменений секретов, и HashiCorp Vault как отдельно отложенная опция на случай роста требований (см. §3).

## 2. Контекст

Приложение использует несколько типов секретов:

1. **API ключи:**
   - API-ключ (или ключ канала доступа) выбранного поставщика модели (сравнение вариантов ведётся в [`ADR_005`](adr_005_first_model_provider_selection.md#adr_005))
   - Telegram bot token ([`BR_006`](../specifications/business_requirements.md#br_006))
   - Внешние интеграции ([`BR_011`](../specifications/business_requirements.md#br_011), [`BR_020`](../specifications/business_requirements.md#br_020))

2. **Учётные данные доступа:**
   - Учётные данные выбранного хранилища данных (сравнение вариантов ведётся в [`ADR_008`](adr_008_data_storage_schema.md#adr_008))
   - SSH ключи для серверов сценариев [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007)

3. **Шифровальные ключи:**
   - ключи, которые должны оставаться вне кода и журналов ([`SEC_CTL_005`](../specifications/system_specification.md#sec_ctl_005), [`INF_REQ_006`](../specifications/infrastructure_baseline.md#inf_req_006))
   - версии ключей, необходимые для контролируемой ротации без скрытой потери доступа

Требования ([`SEC_CTL_005`](../specifications/system_specification.md#sec_ctl_005), [`INF_REQ_006`](../specifications/infrastructure_baseline.md#inf_req_006)):
- Секреты не должны быть в коде или конфигах (git)
- Должна быть возможность ротации без перезагрузки
- Надо контролировать кто получает доступ к чему
- Должна быть возможность аудита (кто достал какой секрет когда)

**Связь с [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007):** ни один из четырёх кандидатов [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007) — Hetzner, DigitalOcean, OVHcloud (сценарий A) и Selectel (сценарий B) — не предоставляет managed-сервис уровня AWS Secrets Manager: это обычные VPS без собственного secrets API. Прежняя версия этого ADR предполагала AWS Secrets Manager и принятие «после выбора площадки» именно потому, что кандидатом облака тогда был AWS; раз AWS в [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007) больше не кандидат, привязка теряет смысл. Практический вывод: выбор способа хранения секретов почти не зависит от того, какой из четырёх кандидатов [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007) победит — на голом VPS одинаково работает любой из вариантов ниже. Единственное, что действительно зависит от исхода [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007), — куда именно на сервере кладётся файл и как он передаётся при `docker run` (детали деплой-скрипта, а не выбор стратегии).

## 3. Предлагаемое решение

Использовать **`.env`-файл на сервере** для проверки в V1:

1. **Хранение:**
   - Один файл `/etc/personal_ai_platform/app.env` (путь уточняется при реализации) с правами `600`, владелец — `deploy`
   - Файл никогда не коммитится в git (`.gitignore`), передаётся на сервер отдельно от кода — вручную по SSH при первом деплое или через тот же безопасный канал, что и SSH-ключи
   - Значения — простые `KEY=VALUE`, без шифрования на диске (сервер и так под контролем через SSH-ключ + firewall из [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007))

2. **Доступ из приложения:**
   - Docker получает секреты через `docker run --env-file /etc/personal_ai_platform/app.env` ([`TASK_008`](../work/tasks/task_008_inf_001.md)) — значения попадают в переменные окружения процесса внутри контейнера, а не в аргументы командной строки (не видны в `docker inspect`/`ps` на хосте)
   - Приложение читает секреты через `os.getenv()` по логическому имени, без прямого доступа к самому файлу

3. **Ротация:**
   - Обновить значение в `.env` на сервере → `docker restart`/`recreate` тем же образом, что и в runbook [`TASK_013`](../work/tasks/task_013_inf_008.md) — перезапуск контейнера, не всей VM
   - Старое значение перестаёт действовать сразу при рестарте; параллельная работа старого/нового ключа не поддерживается (не требуется при ручной, редкой ротации у одного владельца)

4. **Аудит и контроль:**
   - Формального аудита обращений (кто/когда прочитал секрет) на этом уровне нет — при одном владельце и одном сервере это избыточно; [`INF_REQ_006`](../specifications/infrastructure_baseline.md#inf_req_006) требует секреты вне git, а не журнал каждого чтения
   - Контроль доступа обеспечивается тем же SSH-ключом и firewall, что и доступ к серверу вообще ([`ADR_007`](adr_007_cloud_provider_selection.md#adr_007)) — отдельного слоя прав на секреты не заводим

**Согласованный следующий шаг развития — SOPS + age:** тот же `.env`, но хранится в git зашифрованным (расшифровывается в файл на сервере одной командой при деплое). Не меняет фундаментальную стратегию («простой файл на сервере»), только добавляет версионируемую историю *факта* изменения секрета (не самого значения) поверх [`SEC_CTL_005`](../specifications/system_specification.md#sec_ctl_005). Переходить стоит, если понадобится восстановить, какой набор секретов действовал на момент конкретного развёртывания — сейчас такой evidence-потребности нет.

**Отдельно отложенная опция — HashiCorp Vault (self-hosted):** остаётся избыточным, пока верны условия V1 — один владелец, один сервер, ручная редкая ротация. Пересмотреть стоит, если появится любое из: несколько независимых потребителей секретов с разными правами доступа (не один владелец), требование к автоматической ротации без ручного рестарта, или обязательный (а не сознательно опущенный, см. §4) журнал обращений к секретам. До тех пор Vault не разворачивается.

## 4. Альтернативы

| Вариант | Преимущества | Недостатки |
|---------|-------------|-----------|
| **`.env`-файл с правами `600` (выбранный подход)** | Ничего разворачивать не нужно, работает одинаково на любом кандидате [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007) | Ротация вручную; нет журнала обращений; секреты не защищены отдельным шифрованием на диске |
| SOPS + age (согласованный следующий шаг) | Секреты зашифрованы в git, видна история *факта* изменений | Ещё один инструмент в деплой-пайплайне; ключ расшифровки всё равно должен быть на сервере |
| HashiCorp Vault (self-hosted, отложенная опция) | Полноценные ACL, аудит, автоматическая ротация | Отдельный сервис для одного пользователя — нужно поднимать, обновлять и разблокировать после каждого рестарта; явно избыточно для V1 |
| AWS Secrets Manager | Managed, интеграция с IAM и CloudTrail | Не существует ни у одного кандидата ADR_007 — предполагает отдельный, никак не используемый нами облачный аккаунт |
| Экспорт как shell-переменные окружения (`export KEY=...`) | Просто напечатать в терминале | Видны в `ps`/истории команд на сервере — хуже, чем файл с ограниченными правами, при той же простоте |

## 5. Последствия

**Положительные:**
- Секреты не в коде и не в git ([`SEC_CTL_005`](../specifications/system_specification.md#sec_ctl_005), [`INF_REQ_006`](../specifications/infrastructure_baseline.md#inf_req_006))
- Работает одинаково независимо от исхода [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007) — не привязывает эту стратегию к конкретному облаку
- Ничего дополнительного не нужно эксплуатировать (в отличие от Vault) и не нужно оплачивать (в отличие от AWS Secrets Manager)
- Прямой путь апгрейда до SOPS+age без смены фундаментальной стратегии, если появится реальная потребность в истории секретов

**Отрицательные:**
- Ротация полностью ручная — не рассчитана на частую или автоматизированную смену ключей
- Нет журнала обращений к секретам (приемлемо при одном владельце, но зафиксировать как сознательно принятый пробел, а не забытое требование)
- Безопасность файла целиком опирается на защиту самого сервера (SSH-ключ, firewall) — компрометация сервера означает компрометацию всех секретов сразу, без отдельного слоя изоляции

## 6. Проверка

- [ ] `.env`-подход проверен минимум на одном из кандидатов [`ADR_007`](adr_007_cloud_provider_selection.md#adr_007) вместе с реальным деплоем [`TASK_013`](../work/tasks/task_013_inf_008.md).
- [ ] Секреты отсутствуют в коде, git-истории, конфигурации, логах и `docker inspect`/`ps`.
- [ ] Права файла (`600`, владелец `deploy`) подтверждены командой, а не предположением.
- [ ] Процедура ротации (обновить файл → restart/recreate) описана и один раз выполнена вручную.
- [ ] Явно зафиксировано отсутствие журнала обращений как сознательно принятый, а не забытый пробел.
- [ ] Evidence и решение владельца зафиксированы до смены `decision_state`.
