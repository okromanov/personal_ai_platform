# Процедура принятия этапа

## 1. Назначение

Документ описывает, **как явное решение владельца превращается в контролируемое изменение состояния репозитория**. Критерии принадлежат этапу, TEST, доказательствам и профилю качества.

## 2. Предусловия

Переход принятия разрешён только если:

1. Техническое доказательство показывает `ready-for-semantic-review` на конкретном Git SHA. Ни один этап, включая `m01`, не переходит к принятию только по технической готовности — `ready-for-acceptance` без смысловой проверки не наступает.
2. Набор доказательств загружен из артефакта GitHub Actions именно этого SHA и содержит полное покрытие без блокеров. Область изменений считается от начала репозитория для `m01` либо от коммита принятия предыдущего этапа.
3. Для каждого этапа существует отдельная запись смысловой проверки с `result: pass` и `reviewed_sha`, равным SHA доказательства. Для `m01` запись дополнительно подтверждает владельцем состав V1.
4. Все связанные TASK имеют `work_state: completed`. Их завершение не зависит от решения по этапу.
5. Владелец явно даёт команду `ПРИНИМАЮ mXX`.
6. Изменение выполняется на отдельной ветке от SHA доказательства, а не прямой записью в `main`.
7. Получившаяся разница проходит полную проверку проекта.

Команда владельца разрешает всю контролируемую операцию принятия, включая слияние минимального запроса после зелёных проверок.

У этапа основы `m01` может не быть проектных TASK: служебная история создания репозитория и правил управления в очереди проекта не хранится. В этом случае готовность определяется обязательными TEST, доказательствами и смысловой проверкой этапа.

- Доказательства и смысловая проверка остаются привязаны к исходному SHA.
- Коммит принятия получает новый SHA, потому что меняет разрешённые поля состояния и создаёт запись решения.
- Такая разница не является новой содержательной редакцией требований.
- Неожиданная правка останавливает процесс и требует нового доказательства на новом исходном SHA.

## 3. Детерминированный переход

Набор доказательств из артефакта помещается локально, например в `runtime/evidence/latest.json`, после чего выполняется:

```powershell
# Любой этап, включая m01, после ready-for-semantic-review
py operations\scripts\acceptance\apply.py --milestone mXX --owner-confirmation "ПРИНИМАЮ mXX" --evidence runtime\evidence\latest.json --semantic-review runtime\evidence\mXX_semantic_review.json --evidence-repository owner/repo --evidence-workflow "Project check" --evidence-run-id 123 --evidence-run-url https://github.com/owner/repo/actions/runs/123 --evidence-event-sha <40-char-sha> --evidence-artifact-id 456 --evidence-artifact-digest <sha256>
```

Скрипт обязан:

- отказаться работать на `main`/`master`;
- проверить точное совпадение подтверждения владельца с этапом;
- проверить применимое состояние готовности, отсутствие блокеров и покрытие состава;
- проверить точное совпадение `git_sha` доказательства с вершиной ветки;
- проверить смысловую запись `pass` на том же SHA для каждого этапа;
- убедиться, что все связанные TASK уже завершены;
- изменить только заранее предусмотренные поля состояния и создать одну JSON-запись принятия в `work/acceptance/`;
- вложить в запись принятия контрольные суммы, существенные поля технического доказательства и полную смысловую запись, чтобы результат не зависел от временного каталога;
- не менять требования, архитектуру, меры безопасности, содержание ADR или код реализации;
- завершиться ошибкой при неожиданной структуре документа.

Для первоначального `m01` переход меняет `work_state` этапа на `completed`, переводит относящиеся к основе ADR из `decision_state: proposed` в `accepted` и создаёт `work/acceptance/m01.json`. Обычные документы, TASK и TEST не меняются. Их состояния уже отражают действительность независимо от принятия этапа.

Запись принятия использует схему 2. Она не ссылается на игнорируемые файлы `runtime/` как на единственное доказательство. В неё входят:

- Git SHA проверенной редакции;
- контрольная сумма технического доказательства;
- применённая основа покрытия и итог покрытия;
- обязательные сведения о серверном запуске и неизменяемом артефакте;
- полная смысловая запись и её контрольная сумма;
- команда и время решения владельца.

Для последующих этапов процедура по умолчанию меняет только `work_state` этапа и создаёт запись принятия. Расширение правил перехода является обычным изменением средств принятия через запрос на слияние.

## 4. После выполнения

1. Проверить `git diff`. Он должен содержать только разрешённые поля состояния, запись принятия и воспроизводимые производные представления. Ветка создаётся непосредственно от исходного SHA доказательства.
2. Пересобрать производные представления, включая финальный отчёт этапа:
   ```bash
   python3.12 operations/scripts/milestones/update_completion_report.py mXX
   ```
   Отчёт вычисляется из реального состояния репозитория (изменённые файлы, завершённые TASK/TEST, связанные требования), поэтому его нужно пересобрать **после** коммита, меняющего `work_state` этапа на `completed` — до коммита переход ещё не виден истории Git, и отчёт останется в состоянии «в процессе».
3. Запустить полную проверку и модульные тесты.
4. Открыть минимальный запрос на слияние.
5. Слияние выполняется только запросом на слияние с зелёной обязательной серверной проверкой. Команда `ПРИНИМАЮ mXX` задаёт решение владельца, но не отменяет требование запроса и проверки.
6. При неожиданной разнице остановиться и вернуть вопрос владельцу.
7. Только после слияния `main` содержит принятое состояние этапа.

## 5. Что не делает `apply.py`

- сам скрипт не создаёт коммит, не отправляет и не сливает изменения. Эти действия выполняет ограниченная внешняя операция после проверок;
- не пишет напрямую в `main`;
- не создаёт новые полномочия автоматизации;
- не считает подтверждение владельца доказательством технического качества;
- не принимает доказательство от другого Git SHA;
- не исправляет автоматически отсутствующее или неуспешное доказательство.

## 6. Планирование следующего инкремента (V1: m02–m06)

После успешного слияния коммита принятия этапа в `main` система готова к планированию следующего этапа.

Материалы для владельца по конкретному этапу хранятся в `work/mXX/` — по одной папке на этап (например, [`work/m01/`](../work/m01/)). Это отделяет разовые материалы одного этапа от `work/tasks/` и `work/tests/`, которые сквозные для всего проекта.

Единственный файл, который создаётся и обновляется автоматически для каждого этапа, — `final_report.md`: его генерирует `init_milestone.py` при переходе `planned → in-progress` и пересобирает `update_completion_report.py` после принятия (см. шаг 2 выше). Файлы owner_checklist.md и semantic_review.md не генерируются: они создаются вручную только когда этапу действительно нужна запись сверх того, что уже описывают эта процедура и [`operations/semantic_review.md`](semantic_review.md) — пустой шаблон, повторяющий эти документы без уникального содержания, ценности не несёт.

**Важно:** Этапы m02–m06 составляют V1. После m06 завершается версия 1 и начинается планирование V2.

**Для каждого этапа:**

Перед сменой `planned → in-progress` агент сначала создаёт профиль качества, TEST и TASK с явным `component`, затем выполняет:

```bash
python3.12 operations/scripts/milestones/start.py --milestone mXX --dry-run
python3.12 operations/scripts/milestones/start.py --milestone mXX --apply
```

Первый запуск ничего не меняет и выводит все блокеры. Второй повторяет тот же preflight и атомарно меняет только состояние этапа и `updated`.

1. **Автоматическое предложение** — система показывает, что текущий этап завершён:
   - После m01, m02, m03, m04, m05: готов следующий инкремент V1
   - После m06: **V1 завершена**, начинается планирование V2

2. **Запуск stage planning wizard:**
   ```bash
   python3.12 operations/scripts/requirements/stage_planning_wizard.py
   ```

3. **Интерактивное планирование** — wizard собирает:
   - Области фокуса для следующего этапа (integration/storage/ui/automation/security)
   - Ключевые функции и возможности
   - Внешние системы и зависимости
   - Потенциальные риски
   - Критерии успеха

4. **Результат** — roadmap следующего этапа с примерным составом:
   - Для m02–m06: планы инкрементов V1
   - Для m07+: планы инкрементов V2 и далее

5. **Использование плана** — владелец обсуждает план, затем:
   - Агент добавляет требования через `requirement_wizard.py`
   - Каждое BR автоматически интегрируется в состав этапа
   - План служит ориентиром для полноты

Это обеспечивает **непрерывное планирование** между этапами и версиями без перерывов.
