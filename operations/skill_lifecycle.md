# Жизненный цикл скиллов (Skill Hub)

## 1. Назначение

Документ определяет, как внешний или внутренне созданный `Skill` становится частью закрытого внутреннего хаба, кто это проверяет и какие доказательства требуются на каждом шаге.

Экосистема скиллов платформы — **закрытая навсегда**: хаб не является публичным маркетплейсом. Любой скилл — написанный владельцем/агентом с нуля или взятый снаружи — обязан пройти этот цикл прежде, чем он получает право быть вызванным `ARC_CMP_003` (Оркестрация и RuntimePort) как принятая часть системы. Это прямое расширение требования [`SEC_CTL_011`](../specifications/system_specification.md#sec_ctl_011) ("Навык, созданный во время работы, остаётся кандидатом до обычной проверки и принятия") и следствие принципа №1 [`project_rules.md`](../project_rules.md) ("Владелец имеет окончательную власть").

Документ не вводит новый защищённый шаблонный контракт (принцип №18) и не регистрирует `type: skill` в [`change_process.md`](change_process.md#8-стандарт-yaml-frontmatter-и-правила-создания-файлов) §8.1 — это отдельное решение, см. раздел 7.

## 2. Состояния скилла

| Состояние | Описание | Может быть заменено |
|---|---|---|
| `candidate` | Скилл заявлен (создан агентом/владельцем или получен извне), проверка не начата | ✅ Да |
| `in_review` | Идёт проверка источника, лицензии, безопасности, соответствия контракту Capability/Tool | ✅ Да |
| `hardening` | Пройден review, идёт изолированная техническая отработка (eval, тестовый прогон) | ✅ Да |
| `probation` | Пройдена отработка, скилл используется ограниченно под усиленным аудитом ("обкатка") | ✅ Да |
| `accepted` | Скилл принят владельцем и доступен в хабе для обычного вызова | ✅ Да (супсидируется новой версией) |
| `rejected` | Скилл отклонён на любой стадии проверки | ❌ Нет (исторический факт) |
| `retired` | Принятый скилл выведен из хаба (устарел, заменён, отозвано доверие к источнику) | ❌ Нет (архив) |

## 3. Жизненный цикл скилла

### Фаза 0: Заявка (candidate)

**Когда скилл становится кандидатом:**
- Владелец или агент формулирует повторяемый многошаговый сценарий, для которого нет подходящей уже принятой Capability/Skill (см. [`ARC_CMP_003`](../specifications/architecture_baseline.md#arc_cmp_003)).
- Обнаружен готовый внешний скилл (в т.ч. упакованный как plugin по актуальному отраслевому формату), закрывающий требование из [`business_requirements.md`](../specifications/business_requirements.md) с приоритетом `must`/`important`.

**Что делает агент перед заявкой:**
- Проверяет по принципу №12 [`project_rules.md`](../project_rules.md), нет ли уже принятой Capability/Skill/зрелой библиотеки, закрывающей ту же потребность — новый кандидат не создаётся при наличии рабочей альтернативы.
- Если источник внешний и пришёл как plugin-пакет (bundles hooks/subagents/MCP-серверы) — на этом же шаге распаковывает только Skill- и Tool-декларации; `hooks` и любые обработчики жизненного цикла из пакета в кандидата не переносятся и в проверку не попадают в исходном виде (они не должны иметь пути к `ARC_CMP_002`/`ARC_CMP_005`).
- Формулирует владельцу, какую Capability закрывает кандидат и какой `BR_*`/`ARC_CMP_*` он трассирует — без предрешённого выбора реализации.

**Результат фазы:** зафиксированный кандидат с известным источником (`internal` или `external:<имя/URL>`), целевой Capability и трассировкой к требованию.

### Фаза 1: Проверка (in_review)

Проверяются четыре области из [`SEC_CTL_011`](../specifications/system_specification.md#sec_ctl_011):

1. **Источник** — кто автор, репутация, история сопровождения.
2. **Лицензия** — совместимость с [`license_policy.md`](license_policy.md) и закрытым режимом репозитория.
3. **Безопасность** — заявленный класс воздействия (см. `SEC_CTL_008`), запрашиваемые полномочия инструментов через `ARC_CMP_005`, отсутствие скрытых сетевых/файловых обращений сверх заявленных.
4. **Сопровождение** — воспроизводимая версия/ссылка вместо "плавающего" источника (принцип воспроизводимости из `SEC_CTL_011`).

Скилл, запрашивающий полномочия шире минимально необходимых для заявленной Capability (принцип №7 "Минимальные полномочия"), возвращается на доработку или отклоняется — расширение объёма не считается автоматическим правом кандидата.

**Результат фазы:** заключение "допущен к отработке" с зафиксированным списком разрешённых Tool/полномочий, либо `rejected` с причиной.

### Фаза 2: Отработка (hardening)

Техническая проверка в изоляции, без влияния на реальное состояние владельца:

- Прогон в ограниченной рабочей области (`INF_CMP_004`), без доступа к каноническому постоянному хранилищу.
- Проверка против eval/golden cases (см. подход [`operations/eval/golden_cases.json`](eval/golden_cases.json)) и явных негативных сценариев (что скилл не должен делать).
- Проверка идемпотентности повторного вызова и корректного поведения при отказе (принцип №9 "Важные изменения должны быть обратимы").

**Условие перехода дальше:** воспроизводимый зелёный прогон отработки; отчёт с доказательствами прикладывается к заявке кандидата.

### Фаза 3: Обкатка (probation)

Ограниченное реальное использование под усиленным наблюдением до полного доверия:

- Скилл доступен для вызова, но каждый вызов проходит с повышенным уровнем аудита/логирования (`ARC_CMP_009`) и, если класс воздействия это требует, с обязательным подтверждением владельца перед чувствительным действием (`ARC_CMP_002`) — даже если для уже принятых скиллов той же чувствительности подтверждение обычно не требуется.
- Срок и объём обкатки определяются классом воздействия кандидата: чем выше потенциальный ущерб, тем дольше и уже период ограниченного использования.
- Любой сбой, неожиданное поведение или расхождение с заявленным контрактом Capability возвращает кандидата в `in_review` или переводит в `rejected` — обкатка не накапливает "кредит доверия" молча.

**Результат фазы:** набор реальных прецедентов использования без инцидентов, обзор которых предъявляется владельцу для решения.

### Фаза 4: Принятие (accepted)

1. Агент представляет владельцу: что делает скилл, какую Capability закрывает, какие полномочия использует, результаты отработки и обкатки, открытые риски.
2. Только после явного решения владельца скилл переходит в `accepted` и становится доступен в хабе как обычная часть `ARC_CMP_003`.
3. Публикация фиксируется как обычное изменение через `change_process.md` (review + слияние в `main`).

**После принятия:**
- Скилл больше не требует повышенного аудита сверх обычного класса воздействия.
- Изменение принятого скилла (новая версия, новые полномочия, смена источника) — это новый цикл с Фазы 1 для изменённой части, а не тихое обновление на месте.

### Фаза 5: Отклонение (rejected)

Скилл может быть отклонён на любой фазе (0–3):
- источник/лицензия/безопасность не проходят проверку;
- запрашиваемые полномочия шире необходимого и не сужаются по запросу;
- отработка или обкатка вскрывают расхождение с заявленным поведением;
- владелец отклоняет по итогам Фазы 4 без технической причины (окончательное право владельца).

`rejected` — не тупик навсегда для *потребности*: если Capability всё ещё нужна, заводится новый кандидат (другой источник/реализация), а не повторная попытка того же кандидата без изменений.

### Фаза 6: Вывод из хаба (retired)

Принятый скилл выводится, когда:
- Capability, которую он закрывал, больше не нужна (BR удалён/заменён);
- источник отозвал доверие (устарел, скомпрометирован, прекращено сопровождение) — тогда `retired` инициируется немедленно, не дожидаясь планового пересмотра;
- найдена лучшая реализация той же Capability.

`retired` скилл остаётся в архиве (не удаляется), ссылка на замену (если есть) фиксируется явно — аналогично `superseded_by` у ADR.

## 4. Таблица переходов состояний

```
candidate ──→ in_review ──→ hardening ──→ probation ──→ accepted ──→ retired
    │              │              │              │
    └──────────────┴──────────────┴──────────────┴──→ rejected (end)
```

| Переход | Условие | Кто принимает решение |
|---|---|---|
| candidate → in_review | Заявка зафиксирована, источник и целевая Capability известны | Агент (техническая готовность) |
| in_review → hardening | Источник/лицензия/безопасность/сопровождение проверены, полномочия сужены до минимума | Агент, с явной фиксацией заключения |
| in_review → rejected | Проверка не пройдена | Агент представляет причину, владелец подтверждает при спорных случаях |
| hardening → probation | Воспроизводимый зелёный прогон отработки, включая негативные сценарии | Агент |
| hardening → rejected | Отработка вскрыла расхождение с заявленным поведением | Агент представляет причину |
| probation → accepted | Период обкатки пройден без инцидентов, владелец явно согласился | **Только владелец** |
| probation → rejected | Инцидент или расхождение во время обкатки | Немедленно, агент фиксирует, владелец уведомляется |
| accepted → retired | Потребность исчезла, источник скомпрометирован, найдена замена | Владелец (или немедленно при отзыве доверия к источнику) |

## 5. Черновой набросок полей (не формализовано)

Ниже — рабочий набросок того, какие поля потребуются кандидату скилла, если/когда `type: skill` будет формально зарегистрирован в [`change_process.md`](change_process.md#8-стандарт-yaml-frontmatter-и-правила-создания-файлов) §8.1 и в `operations/scripts/documents/traceability.py` (см. раздел 7 — это отдельное решение, здесь только черновик для обсуждения):

```yaml
---
id: SKL_XXX
type: skill
skill_state: candidate|in_review|hardening|probation|accepted|rejected|retired
source: internal|external:<источник>
version: 1.0
updated: <дата>
traces_to:
  - <BR_XXX, ARC_CMP_003>
implements_capability: <CAP_XXX или описание Capability>
requires_tools:
  - <ARC_CMP_005-совместимый список Tool с классом воздействия>
retired_by: SKL_YYY  # только если skill_state: retired и есть замена
---
```

## 6. Пример сценария

### Сценарий: внешний скилл под уже существующую Capability

```
1. Найден зрелый сторонний скилл, закрывающий Capability "работа с календарём"
   (уже определённую под BR с приоритетом important)
2. Зафиксирован как candidate, source: external:<репозиторий>
3. Фаза 1: лицензия совместима, сопровождение активно, запрошенные полномочия
   сужены до чтения календаря без права удаления событий
4. Фаза 2: отработка в изолированной области, зелёный прогон против golden cases
5. Фаза 3: обкатка 2 недели с подтверждением владельца перед каждым чувствительным
   вызовом (создание/изменение события), инцидентов нет
6. Владелец рассматривает сводку и явно принимает скилл
7. skill_state: accepted, скилл доступен в хабе без повышенного аудита
```

## 7. Открытый вопрос для владельца

Этот документ описывает процесс, но **не** делает `SKL_XXX` проверяемым идентификатором наравне с `ADR_XXX`/`TASK_XXX` — для этого нужно отдельное решение: добавить `type: skill` в `change_process.md` §8.1 (защищённый authority-документ) и научить `operations/scripts/documents/traceability.py` распознавать `SKL_*`/`implements_capability`. Пока это не сделано, цикл выше — согласованный процесс, но не автоматически проверяемый CI контракт. Нужно ли формализовать это сейчас как отдельный contract-PR, или оставить как процессное описание до появления первого реального кандидата скилла?
