# Жизненный цикл архитектурных решений (ADR)

## 1. Назначение

Документ определяет, как создаются, обновляются и архивируются ADR на всех этапах проекта.

## 2. Состояния ADR

| Состояние | Описание | Может быть заменено |
|---|---|---|
| `proposed` | Решение предложено и ждёт утверждения | ✅ Да |
| `accepted` | Решение утверждено и действует | ✅ Да (супсидировано новым) |
| `rejected` | Решение отклонено после обсуждения | ❌ Нет (исторический факт) |
| `superseded` | Решение заменено другим ADR | ❌ Нет (сохраняется история) |

## 3. Жизненный цикл ADR

### Фаза 1: Создание (proposed)

**Когда создается ADR:**
- Обнаружен реальный значимый выбор между альтернативами
- Решение имеет устойчивые последствия (дорого менять)
- Определяет важную техническую границу
- На него ссылаются несколько частей системы

**Условия создания:**
- Все альтернативы сравнены на реальном примере
- Есть обоснование выбора (раздел "Последствия")
- Указан требование (поле `traces_to_requirement`)
- Создана в папке `adr/` с ID `ADR_XXX`

**Проверка перед утверждением:**
```bash
python3.12 operations/scripts/documents/check.py --all
```

Должны пройти проверки: `traceability`, `document_policy`.

### Фаза 2: Принятие (accepted)

**Как ADR переходит в accepted:**
1. Автор создаёт PR с ADR (decision_state: proposed)
2. Проводится обсуждение (review comments на PR)
3. После одобрения обновляется decision_state: accepted
4. PR мержится в main

**После принятия:**
- ADR становится "правилом игры" для реализации
- Нижние слои (ARC, INF, имплементация) должны ему следовать
- Изменение accepted ADR требует новой версии или нового ADR

### Специальный случай: ADR для m01

ADR, явно связанные с этапом m01 машинным полем `traces_to: m01`:
- Остаются в `decision_state: proposed` пока находятся в ветке разработки
- Переходят в `decision_state: accepted` **при принятии m01** через скрипт `operations/scripts/acceptance/apply.py`
- Это исключение из обычного процесса PR-обсуждения, так как m01 охватывает установление базовых правил проекта

Комментарий в тексте, ссылка из другого документа или неявная зависимость не заменяют `traces_to: m01`: `apply.py` не должен угадывать намерение.

Для остальных ADR (создаваемых независимо от конкретного этапа):
- Переход в `accepted` происходит при завершении PR-обсуждения и слиянии в main
- Не привязано к принятию конкретного этапа

### Фаза 3: Замена (superseded)

**Когда ADR заменяется:**
- Требование (`traces_to_requirement`) изменилось или удалено
- Найдено лучшее решение той же проблемы
- Технология или контекст настолько изменились, что решение больше не применяется

**Процесс замены:**

1. Создать новый ADR с новым решением (decision_state: proposed)
2. В старом ADR обновить:
   - `decision_state: superseded`
   - Добавить `superseded_by: ADR_XXX` (новый ADR)
   - Добавить примечание в раздел "Последствия"
3. Старый ADR остаётся в архиве (не удаляется!)
4. Слить через PR

**Пример в старом ADR:**
```markdown
## 5. Последствия

...

### Nota bene: Замена
Это решение заменено ADR_005 после переоценки требований в m03.
Причина: требование SEC_CTL_010 было удалено из V1.
```

### Фаза 4: Отклонение (rejected)

**Когда ADR отклоняется:**
- После обсуждения команда решила не принимать предложение
- Выбрано альтернативное решение
- Требование было отложено за пределы текущего этапа

**Процесс отклонения:**

1. В PR добавить review comment с причиной
2. Обновить decision_state: rejected
3. Добавить примечание в раздел "Последствия" (почему отклонено)
4. Можно не мержить PR (история остаётся в PR)

**Пример:**
```markdown
## 5. Последствия

...

### Отклонение
Это решение было отклонено на основе feedback в PR#42.
Причина: требуемый компонент находится в ранней разработке;
рекомендуется пересмотреть на m03 когда компонент готов.
```

## 4. Переоценка ADR

**Кто переоценивает:**
- Автор требования (SYS/SEC/ARC), на которое ссылается ADR
- Разработчик, обнаруживший проблему с реализацией
- Владелец проекта в конце этапа

**Когда переоценивать:**
- Требование изменилось → может потребоваться другое решение
- Найдена проблема в реализации → решение неполно или неправильно
- Технология эволюционировала → есть лучший вариант
- Опыт реальной эксплуатации показал проблему

**Процесс переоценки:**

1. Создать issue или обсудить в PR
2. Если решение всё ещё верно → добавить примечание (комментарий версии)
3. Если нужно поменять → создать новый ADR (superseded)
4. Если решение проблемно → рассмотреть rejected или супсидирование

## 5. Поля ADR для управления жизненным циклом

Каждый ADR должен иметь:

```yaml
---
id: ADR_XXX
type: adr
decision_state: proposed|accepted|rejected|superseded
version: 1.0
updated: <текущая дата>
traces_to:
  - <реализует что: SYS/ARC/INF ID>
traces_to_requirement:
  - <зависит от: SYS_XXX>
superseded_by: ADR_YYY  # Только если superseded
---
```

- `superseded_by` используется ТОЛЬКО если `decision_state: superseded`
- `version` увеличивается если требование из `traces_to_requirement` изменилось и повлияло на решение
- `updated` отражает день последнего пересмотра (не обязательно смены версии)

## 6. Таблица переходов состояний

```
proposed ──→ accepted ┐
    ↓                 │
rejected          superseded
(end)             (archive)
```

| Переход | Условие | Тип изменения |
|---|---|---|
| proposed → accepted | PR одобрен | Слияние в main, version не меняется |
| proposed → rejected | PR отклонен | Опциональное слияние (история), version не меняется |
| accepted → superseded | Требование изменилось или найдено лучшее решение | Новый PR, создать новый ADR, старый помечен |
| rejected → (нет) | Отклонённое решение остаётся архивом | Просмотр истории |

## 7. Архив ADR

**Где хранятся старые ADR:**
- Папка `adr/` содержит ВСЕ ADR (включая rejected и superseded)
- Старые решения никогда не удаляются (важны для истории)
- Ссылки на superseded ADR сохраняются в новом ADR (поле `superseded_by`)

**Как найти активное решение:**
1. Прочитать требование (SYS/ARC/SEC/INF ID)
2. Найти ADR через `traces_to_requirement`
3. Если `decision_state: superseded` → перейти по `superseded_by`
4. Если `decision_state: accepted` → это действующее решение
5. Если `decision_state: rejected` → решение не применяется

## 8. Примеры сценариев

### Сценарий A: Новое требование → новый ADR

```
1. Создано требование SYS_030
2. Найти лучший технологический вариант
3. Сравнить 2-3 варианта на примере
4. Создать ADR_015 с выбранным решением
   traces_to_requirement: [SYS_030]
5. PR → обсуждение → accepted
```

### Сценарий B: Требование удалено → ADR архивируется

```
1. SYS_030 удалено из спецификации
2. ADR_015 больше не нужен
3. Создать ADR_016 (новое решение для замены)
   superseded_by: ADR_016
4. Обновить ADR_015 decision_state: superseded
5. PR с обоими ADR → мержить
```

### Сценарий C: Требование изменилось → пересоздать ADR

```
1. SYS_030 изменило область или фокус
2. ADR_015 больше не полностью покрывает требование
3. Создать ADR_017 с переоцененным решением
   traces_to_requirement: [SYS_030]  # то же требование
4. Обновить ADR_015:
   decision_state: superseded
   superseded_by: ADR_017
5. PR → мержить оба ADR
```

## 9. Проверки на соответствие жизненному циклу

В `check.py` нет встроенной проверки, но можно вручную:

- Все ADR имеют `traces_to_requirement`?
- Если `superseded` → указан `superseded_by`?
- Если `superseded_by: ADR_YYY` → ADR_YYY существует?
- `updated` соответствует дате последнего изменения?

Эти проверки станут частью future проекта (m03+).
