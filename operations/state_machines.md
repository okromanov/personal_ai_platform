# Диаграммы состояний и переходы

Этот документ определяет действительные переходы состояния для всех типов сущностей в проекте. Переходы, не указанные явно, недопустимы и должны быть заблокированы технически.

## 1. Состояния задач (work_state)

Задачи проходят следующие состояния в процессе реализации:

```
┌────────────┐
│  planned   │
└─────┬──────┘
      │
      ▼
┌─────────────────┐
│  in-progress    │
└─────┬──────┬────┘
      │      │
      │      ▼
      │   ┌─────────────┐
      │   │  blocked    │
      │   └──────┬──────┘
      │          │
      │          ▼
      │   ┌─────────────┐
      │   │ in-progress │
      │   └─────────────┘
      │
      ▼
┌─────────────┐
│ completed   │
└─────────────┘

┌────────────┐
│  planned   │
└─────┬──────┘
      │
      ▼
┌──────────────┐
│  cancelled   │
└──────────────┘
```

### Допустимые переходы

| От | К | Условие | Действие |
|---|---|---|---|
| `planned` | `in-progress` | Начало работы | Задача активирована |
| `in-progress` | `blocked` | Обнаружена зависимость | Задача заблокирована |
| `blocked` | `in-progress` | Блокировка разрешена | Задача возобновляется |
| `in-progress` | `completed` | Работа завершена | Задача принята владельцем |
| `planned` | `cancelled` | Отмена владельцем | Задача отменяется |
| `in-progress` | `cancelled` | Отмена владельцем | Задача отменяется |
| `blocked` | `cancelled` | Отмена владельцем | Задача отменяется |

### Финальные состояния

- `completed`: Задача выполнена и принята.
- `cancelled`: Задача отменена и не будет выполняться.

Финальные состояния неизменяемы.

## 2. Состояния документов (document_state)

Документы источников истины проходят следующие состояния жизненного цикла:

```
┌─────────┐
│ current │
└────┬────┘
     │
     ▼
┌────────────┐
│ superseded │
└────────────┘
```

### Допустимые переходы

| От | К | Условие | Действие |
|---|---|---|---|
| `current` | `superseded` | Новый документ заменил текущий | Документ архивируется |
| `superseded` | `current` | Восстановление предыдущей версии (редко) | Документ активируется |

### Особенности

- Документ может быть помечен `superseded` с указанием нового документа через поле `superseded_by`.
- Переход только в одну сторону для normal flow (current → superseded).
- Восстановление возможно только явно и требует обоснования.

## 3. Состояния решений (decision_state для ADR)

Архитектурные решения проходят жизненный цикл принятия:

```
┌──────────┐
│ proposed │
└────┬─────┘
     │
     ├─────────────────┐
     ▼                 ▼
┌──────────┐      ┌──────────┐
│ accepted │      │ rejected │
└────┬─────┘      └──────────┘
     │
     ▼
┌────────────┐
│ superseded │
└────────────┘
```

### Допустимые переходы

| От | К | Условие | Действие |
|---|---|---|---|
| `proposed` | `accepted` | Решение принято владельцем | Решение внедряется |
| `proposed` | `rejected` | Решение отклонено | Решение архивируется |
| `accepted` | `superseded` | Новое решение заменило старое | Решение помечается устаревшим |

### Особенности

- `proposed`: Решение предложено но не принято. Может быть изменено или отклонено.
- `accepted`: Решение одобрено. Компоненты должны следовать этому решению.
- `rejected`: Решение отклонено. Документируется, почему не было принято.
- `superseded`: Решение заменено новым. Указывается новое решение в `superseded_by`.

## 4. Состояния проверок (spec_state для TEST)

Спецификации тестов проходят следующие состояния:

```
┌─────────┐
│ current │
└────┬────┘
     │
     ▼
┌────────────┐
│ superseded │
└────────────┘
```

### Допустимые переходы

| От | К | Условие | Действие |
|---|---|---|---|
| `current` | `superseded` | Новый тест заменил текущий | Тест архивируется |

### Особенности

- Идентичны состояниям документов (`document_state`).
- Устаревший тест должен указывать на новый через `superseded_by`.

## 5. Состояния этапов (`work_state`)

Каждый milestone имеет явное поле `work_state` в [`milestones.md`](../milestones.md). Готовность к смысловой проверке и принятию вычисляется из доказательств и не является отдельным редактируемым состоянием.

```
planned
   │
   ▼
in-progress
   │
   ├─────────────────────┐
   │                     │
   ▼                     ▼
технически готов    blocked
   │                     │
   │                     ▼
   │              Требуется доработка
   │                     │
   │                     └────┬─────┘
   │                          │
   │                          ▼
   │                      Работа
   │
   ▼
смысловая проверка + решение владельца
   │
   ▼
completed
```

### Логические переходы

| От | К | Условие | Проверка |
|---|---|---|---|
| `planned` | `in-progress` | Есть профиль, полное TEST-покрытие и семантические TASK→component→requirements связи | `start.py --dry-run`, затем `start.py --apply` |
| `in-progress` | `blocked` | Выявлена внешняя или техническая блокировка | Причина наблюдаема |
| `blocked` | `in-progress` | Блокировка устранена | Проверки повторены |
| `in-progress` | `completed` | Технические доказательства, свежая смысловая проверка и точная команда владельца | `apply.py` и отдельный acceptance PR |

### Особенности

- `work_state` — единственное редактируемое состояние milestone; `ready-for-semantic-review` и `ready-for-acceptance` — вычисляемые режимы готовности.
- Транзакция: если хотя бы одна проверка не пройдена, этап не может быть принят.
- Начало этапа атомарно: [`operations/scripts/milestones/start.py`](scripts/milestones/start.py) сначала выполняет полный preflight без записи и меняет только `work_state` и `updated` после успеха всех условий.
- Откат: владелец может отклонить этап на принятие, тогда работа продолжается.

## 6. Переходы, которые НЕДОПУСТИМЫ

Следующие переходы должны быть технически заблокированы и никогда не допущены:

### Для задач

- `completed` → любое другое состояние (финальное)
- `cancelled` → любое другое состояние (финальное)
- `in-progress` → `planned` (откат запрещён)
- `blocked` → `completed` (нужно вернуться в progress сначала)

### Для документов

- `superseded` → `current` без явного восстановления (редко и требует обоснования)

### Для решений

- `rejected` → `accepted` (отклонённое решение не возвращается)
- `superseded` → `accepted` (устаревшее решение не активируется)

### Для проверок

- `superseded` → `current` без явного восстановления

## 7. Правила для переходов состояния

1. **Атомарность**: Переход состояния должен быть атомарен. Если переход начался, он должен завершиться полностью или откатиться полностью.

2. **Логирование**: Каждый переход состояния должен быть залогирован с временной меткой, кто инициировал и почему.

3. **Валидация**: Перед переходом должны быть проверены все предусловия. Если предусловия не выполнены, переход блокируется.

4. **Невозвратность**: Финальные состояния неизменяемы (completed, cancelled, rejected).

5. **Родительские состояния**: Если сущность имеет родителя (например, тест относится к этапу), переход состояния дочерней сущности не должен нарушить консистентность родителя.

## 8. Примеры правильных сценариев

### Сценарий 1: Нормальное завершение задачи

```
TASK_001: planned 
    → in-progress (агент начал работу)
    → completed (агент завершил работу, владелец принял)
```

### Сценарий 2: Задача была заблокирована

```
TASK_001: planned 
    → in-progress (агент начал работу)
    → blocked (обнаружена зависимость)
    → in-progress (зависимость разрешена)
    → completed (работа завершена)
```

### Сценарий 3: принятый ADR был заменён

```
ADR_100: accepted (решение было принято)
    → superseded (новое решение заменило старое - ADR_101)
```

### Сценарий 4: Тест был заменён

```
TEST_001: current (исходный тест)
    → superseded (новый тест - TEST_001_v2 - лучше и полнее)
```
