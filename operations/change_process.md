# Процедуры изменений и публикации

## 1. Назначение

Документ отвечает на вопрос: **как вносятся изменения в репозиторий, как управляются ветки, версии документов и доказательства готовности**.

Процедурные вопросы (кто и когда) отвечает [`project_rules.md`](../project_rules.md). Конкретные технические команды находятся в [`operations/local_development_windows.md`](local_development_windows.md).

## 2. Изменения и публикация

Создание коммита или запроса на слияние является предложением изменения, а не подтверждением результата.

- Все изменения агента выполняются в отдельной ветке и попадают в `main` только через запрос на слияние.
- Один связный запрос может содержать код, проверки и все связанные документы. Отдельный запрос для каждого файла не нужен.
- Изменение принципов и принятие этапа всегда выполняются через отдельный запрос на слияние.
- Правка машинерии качества — `.github/workflows/**`, `operations/hooks/**`, `operations/scripts/quality/**`, `operations/scripts/documents/**` — не смешивается в одном запросе с продуктовой поставкой (`src/**`, `adr/**`, `dockerfile`). Границы TASK её не покрывают: она исключена вместе со всем `operations/**`, а обоснование «правку видно через обязательную смену версии» к `.py` и `.yml` неприменимо — поля `version` у них нет. Иначе ослабление проверки уезжает внутрь продуктового PR, где на него не смотрят. Проверяется автоматически в `check_change_scope.py`.
- Целевой режим `main`: изменение только через запрос на слияние, обязательная серверная проверка, запрет принудительного изменения и удаления ветки. Текстовая команда не отменяет эти ограничения.
- GitHub Actions на каждом `push` в `main` сверяет SHA со слитым запросом. Прямая запись останется в истории, но будет автоматически обнаружена, а `Project check` не станет доказательством готовности.
- Штатная автоматизация имеет только читающие полномочия. Единственное исключение — узкий workflow `delete_merged_branches.yml`; учётные данные агента разработки отдельно позволяют публиковать ветки и запросы на слияние, без этого он не может предъявить результат.
- Полномочия и область этого workflow: только `contents: write` и `pull-requests: read`; запуск после успешного слияния same-repository PR. По решению владельца он удаляет слитые ветки любого имени, а не только `codex/*`.
- Границу держит не префикс имени, а три условия: ветка не является веткой по умолчанию, не защищена, и GitHub подтверждает для неё слитый PR. Единственное изменяющее обращение, которое ему разрешено, — удаление ref такой ветки; это проверяется по белому списку в `check_automation_policy`.
- Изменение полномочий владельца или критической границы безопасности всегда выполняется через отдельный запрос на слияние.
- Иные штатные workflow остаются только читающими. Разрешение на очистку веток нельзя использовать для изменения файлов, тегов, releases или несвязанных refs.
- Автоматизация не может сама расширить список файлов, учётных данных или типов решений, которые имеет право изменять.

### 2.1 Изменение защищённого шаблонного контракта

Новый, удалённый, переименованный, перенумерованный или перемещённый заголовок `##` в документе шаблонного типа является изменением контракта, даже если правится только один экземпляр, а файл шаблона пока не затронут. Команда исправить документ, TASK `allowed_paths` или зелёный checker не дают разрешения расширить структуру.

До изменения агент обязан остановиться и задать владельцу один вопрос со следующими частями:

1. точный предлагаемый заголовок и его место;
2. причина, которую нельзя закрыть содержанием существующего раздела или подразделом `###`;
3. затрагиваемые типы, шаблоны, renderer-функции и существующие документы;
4. миграция уже созданных файлов;
5. изменение блокирующей проверки и negative regression-tests.

Только явное подтверждение этого предложения разрешает отдельный contract-PR. В нём сначала синхронно изменяются шаблон, renderer, checker, tests и существующие экземпляры; использование новой структуры до прохождения этого PR запрещено. При отсутствии решения документ сохраняет текущий контракт, а новый материал помещается в подходящий существующий раздел.

## 3. Типизированные состояния и версия

Допустимые значения определены один раз в [`document_contracts.json`](document_contracts.json); таблица ниже объясняет их человеку. Checker и генераторы читают машинный контракт, а не копируют множества значений.

Поле `applicability` отделяет применимость от жизненного состояния: `normative` — действующее правило, `reference` — справка, `proposed` — неактивное предложение, `historical` — архив. Если поле отсутствует, применяется `normative`; `document_state: superseded` требует `applicability: historical`.

Универсальное поле `status` запрещено для первичных документов: оно смешивает состояние документа, решения, работы и результата проверки. Каждый тип использует собственное поле.

| Объект | Поле | Допустимые значения |
|---|---|---|
| Обычный первичный документ | `document_state` | `current`, `superseded` |
| ADR | `decision_state` | `proposed`, `accepted`, `rejected`, `superseded` |
| TASK | `work_state` | `planned`, `in-progress`, `blocked`, `completed`, `cancelled` |
| TEST specification | `spec_state` | `current`, `superseded` |
| Результат запуска | `result` | `passed`, `failed`, `blocked`, `missing` |

Смысловая проверка правки существует на уровне ветки и запроса на слияние. Она не кодируется состоянием `in-review` внутри файла в `main`. Значение `document_state: current` означает только текущую каноническую редакцию. Факт принятия этапа хранится отдельной записью и не требует массовой смены метаданных документов.

Каждая смысловая редакция документа увеличивает младший номер: `1.0 → 1.1 → 1.2`. Правило действует и до принятия базовой редакции: версия отражает собственную историю документа, а не факт принятия этапа, поэтому документы базовой редакции не обязаны оставаться на `1.0`. Новая старшая редакция (`2.0`) создаётся только явным решением владельца.

Поле `updated` показывает день собственного изменения документа. Запрос на слияние сверяет его с датой коммита, фактически изменившего этот документ: правдоподобная, но неверная дата иначе ничем не обнаруживается.

[`project_rules.md`](../project_rules.md), [`AGENTS.md`](../AGENTS.md) и ключевые спецификации задают полномочия и потому не могут меняться без новой версии. Служебная правка этих файлов не создаёт TASK и не покрывается границами путей, поэтому смена версии остаётся единственным обязательным следом такого изменения.

Производные и временные доказательства не используют версию документа как счётчик запусков. Запуск однозначно определяется Git SHA и метаданными доказательства.

## 4. Когда нужен ADR

ADR создаётся только если существует реальный значимый выбор между альтернативами и решение:

- имеет устойчивые последствия;
- дорого или рискованно менять;
- определяет важную техническую границу;
- либо на него будут ссылаться несколько частей системы.

ADR не создаётся, чтобы заранее закрепить гипотетическую технологию. Среда агента, облачный поставщик, хранилище секретов и данных, изоляция кода, VPN, планировщик или средство создания документов фиксируются в ADR только после сравнения актуальных вариантов и принятия решения.

### 4.1 Трассировка требований в ADR

Каждый ADR должен явно указывать, какое требование (SYS, ARC, SEC, INF) он решает. Это помогает:

- отследить, когда требование изменилось, чтобы переоценить решение;
- убедиться, что решение остаётся актуальным;
- удалить ADR, если требование больше не применяется.

Поле `traces_to: [SYS_001, ...]` (см. обязательные поля ADR в разделе 3) указывает на требования вверх по иерархии. Это не подтверждает реализацию, а фиксирует связь решения с требованием.

Если ADR решает несколько требований — перечислить все. Если требование устарело — пересмотреть ADR и обновить decision_state (rejected, superseded) либо обновить traces_to.

## 5. Простота, повторное использование и удаление сложности

Перед собственной реализацией типовой возможности рассматривается последовательность: существующая возможность платформы → стандартная библиотека или протокол → зрелый проект с открытым исходным кодом → тонкий переходный слой → небольшое исправление исходного проекта → ответвление → собственная реализация.

Выбор определяется не популярностью самой по себе, а соответствием требованиям, лицензией, сопровождением, безопасностью, зависимостями, сложностью интеграции и возможностью отката.

Симметрично созданию действует правило удаления сложности:

- неиспользуемая возможность, интеграция или автоматизация должна быть удалена либо явно переведена в неактивное или заменённое состояние;
- ADR пересматривается, если исчезли его предпосылки или выбранный механизм больше не используется;
- лишний переходный слой не сохраняется ради гипотетического будущего;
- зависимость, требующая непропорционального сопровождения, заменяется или удаляется при наличии более простого достаточного пути;
- периодическая оценка после реальной эксплуатации ищет не только новые функции, но и кандидатов на упрощение.

Удаление значимого элемента по умолчанию выполняется через запрос на слияние. Проверяются входящие связи и перенос либо удаление связанных данных. Точная прямая команда владельца применяется только в границах раздела 2.

## 6. Горизонт детализации

Бизнес-потребность может быть зафиксирована заранее как `BR_*`. Более подробные `SYS_*`, `THR_*`, `SEC_CTL_*`, `ARC_*` и `INF_*` добавляются, когда они помогают принять решение, определить устойчивый инвариант, ограничить реальный риск или подготовить проверяемую реализацию. Для далёкого направления предпочтителен уровень `BR_*`, пока детали не определены.

Допустимо заранее сохранить короткое стабильное системное требование, если его смысл ясен и не требует преждевременного выбора технологии. Его наличие не обязывает немедленно реализовывать возможность, инфраструктуру или доказательства. Это определяется текущим этапом и профилем качества.

Если новая сущность не улучшает ближайшее решение, реализацию, риск или проверку, предпочтение отдаётся отсутствию новой сущности до момента фактической необходимости.

Продуктовый документ, который сохраняет уже принятые владельцем решения для будущего цикла, создаётся только в [`candidates/`](../candidates/) с `applicability: proposed` и входящей ссылкой из пункта конкретного будущего этапа [`milestones.md`](../milestones.md).
Когда этот пункт наступает, кандидат обязательно пересматривается: подтверждённый смысл переносится в нормативные спецификации и связанные ADR/TASK, отложенный остаётся кандидатом с новой точкой пересмотра, отклонённый больше не участвует в планировании.
Операционные каталоги не используются как хранилище продуктового бэклога.

## 7. Границы и пересмотр спецификаций

### 7.1 Полнота декомпозиции этапа

Перед началом этапа и перед его принятием агент обязан проверить не только формальную цепочку `scope → component → TASK → TEST`, но и результат, сформулированный в строке `результат` этапа. Для каждого внешне наблюдаемого результата должны существовать: отдельная TASK, реализующая именно интеграцию, и TEST/evidence, проверяющий её в соответствующей внешней среде. Контракты, заглушки, unit-тесты и `allowed_paths` не заменяют это доказательство.

Если в результате этапа названы внешний канал, реальный поставщик, постоянно работающая среда, VPN или иной внешний контур, независимый аудит обязан проверить их как фактические зависимости. Отсутствие хотя бы одной TASK или доказательства фиксируется как `high` finding «неполная декомпозиция этапа»; этап не принимается.

Для каждого нового этапа в [`milestones.md`](../milestones.md) после подэтапов создаётся краткий раздел «Очередь, закрывающая пользовательский результат»: он перечисляет terminal TASK, без которых результат этапа нельзя считать поставленным. Этот раздел — вход для автоматической проверки, которую следует добавить до старта следующего нового этапа.

Отдельно выполняется обратный проход по строке «ADR этого этапа». До перевода milestone из `planned` в `in-progress` каждый ADR со статусом `proposed` получает ровно одну незавершённую TASK-владельца решения через поле `decides`. Для уже активного или заблокированного этапа такая связь обязательна немедленно. TASK должна относиться к тому же milestone, собрать сравнение/evidence и получить явное решение владельца; её нельзя завершить или отменить, пока назначенный ADR остаётся `proposed`. Для
далёкого milestone в `planned` TASK разрешено не создавать до его фактической декомпозиции, но старт такого milestone без назначения всех его `proposed` ADR блокируется checker.

Спецификации содержат только предметную модель и не завершаются процессными разделами о том, кто, когда и как должен их менять.

- [`specifications/architecture_baseline.md`](../specifications/architecture_baseline.md) содержит только устойчивые логические компоненты и потоки. Физические роли, сеть, хранение и развёртывание принадлежат [`specifications/infrastructure_baseline.md`](../specifications/infrastructure_baseline.md). Конкретный устойчивый выбор реализации принадлежит ADR.
- [`specifications/infrastructure_baseline.md`](../specifications/infrastructure_baseline.md) содержит только инфраструктурные требования, компоненты и потоки. Конкретные поставщики, форма вычислений, реализация сети, хранилище секретов, база данных, резервное копирование и средства развёртывания фиксируются ADR только после реального выбора. Пошаговые команды и изменяемые рабочие значения принадлежат [`operations/`](./).
- [`specifications/threat_model.md`](../specifications/threat_model.md) содержит только активы, границы доверия и каталог угроз. Порядок поставки остаётся в [`milestones.md`](../milestones.md), а технические меры — в [`specifications/system_specification.md`](../specifications/system_specification.md).

Модель угроз пересматривается при появлении:

- нового внешнего канала или интеграции;
- нового класса данных или постоянного состояния;
- нового способа исполнения кода или обработки файлов;
- нового типа внешнего действия;
- автономного расписания или многопользовательского доступа;
- изменения полномочий среды или инструмента;
- существенного механизма развёртывания, обновления или нового класса зависимости.

Пересмотр отвечает на три вопроса: появился ли новый `THR_*`, изменился ли существующий риск и достаточно ли связанных `SEC_CTL_*`.

Базовая архитектура и инфраструктура пересматриваются только при изменении устойчивого логического или физического инварианта. Смена поставщика, реализации среды, канала интеграции или эксплуатационного инструмента сама по себе не требует изменения спецификации, пока сохраняются её роли, полномочия, данные и контракты.

### 7.2 Архитектурная визуализация после завершения TASK

Каждый переход TASK в `completed` запускает в полном gate проверку архитектурной визуализации. Проверка сравнивает базовый и новый SHA и определяет, изменились ли разделы `ARC_CMP_*`/`ARC_FLOW_*`, `INF_CMP_*`/`INF_FLOW_*` либо уже отображаемые на схеме `SEC_CTL_*`.

Если отображаемый смысл не изменился, gate явно сообщает, что перерисовка не требуется. Если изменился хотя бы один такой раздел, тот же changeset обязан содержать обновлённый [`personal_ai_platform_architecture.svg`](../work/artefacts/architecture/personal_ai_platform_architecture.svg), увеличенный `diagram_version`, актуальные `source`/`generated_at` и содержательное изменение тела SVG. Изменение только блока метаданных или видимой строки версии блокируется как фиктивная перерисовка.

Автоматизация не выводит архитектуру из реализации и не сочиняет смысл схемы: первичными остаются спецификации, агент выполняет перерисовку по ним, а gate доказывает, что обязательный шаг не пропущен. Реализационная правка без изменения устойчивого инварианта не вызывает бессодержательного изменения SVG.

## 8. Стандарт YAML frontmatter и правила создания файлов

Все документы в репозитории, кроме генерируемых и временных, содержат YAML frontmatter — структурированную метаинформацию в начале файла между тройными дефисами `---`. Это необходимо для валидации, трассировки, версионирования и автоматизации.

### 8.1 Требуемые и опциональные поля по типу документа

**Первичные документы** (правила, спецификации, требования, инструкции, процедуры):

Обязательные поля:
- `id` — уникальный идентификатор в формате `snake_case` (например `project_rules`, `system_specification`)
- `type` — строковый тип документа (например `project_rules`, `business_requirements`, `system_specification`, `agent_instruction`, `operations`, `architecture_baseline`, `threat_model`)
- `document_state` — текущее состояние, допустимые значения: `current`, `superseded`
- `version` — номер версии в формате `X.Y` (стартует с `1.0`, младший номер растёт при каждой смысловой правке)
- `updated` — дата последнего изменения в формате `YYYY-MM-DD`
- `depends_on` — список ID документов, от которых зависит этот, может быть пустым `[]`

Пример:
```yaml
---
id: system_specification
type: system_specification
document_state: current
version: 1.0
updated: 2026-08-18
depends_on:
  - business_requirements
  - threat_model
  - project_rules
---
```

**Архитектурные решения (ADR)**:

Обязательные поля:
- `id` — формат `ADR_XXX` где `XXX` — трёхзначный номер
- `type` — значение `adr`
- `decision_state` — допустимые значения: `proposed`, `accepted`, `rejected`, `superseded`
- `version` — номер версии в формате `X.Y`
- `updated` — дата последнего изменения
- `traces_to` — список ID требований (SYS, SEC_CTL, INF, ARC), на которые ссылается решение, может быть пустым `[]`

Пример:
```yaml
---
id: ADR_001
type: adr
decision_state: proposed
version: 1.0
updated: 2026-08-18
traces_to:
  - SYS_001
  - INF_REQ_001
---
```

**Проектные задачи (TASK)**:

Обязательные поля:
- `id` — формат `TASK_XXX` где `XXX` — трёхзначный номер (стартует с [`TASK_001`](../work/tasks/task_001_arc_001.md))
- `type` — значение `task`
- `title` — короткое название задачи
- `component` — ровно один `ARC_CMP_*`, `ARC_FLOW_*`, `INF_CMP_*` или `INF_FLOW_*`, поставляемый задачей
- `work_state` — допустимые значения: `planned`, `in-progress`, `blocked`, `completed`, `cancelled`
- `version` — номер версии
- `updated` — дата последнего изменения
- `depends_on` — список предыдущих TASK, для [`TASK_001`](../work/tasks/task_001_arc_001.md) может быть пустым `[]`
- `next_actor` — кто выполнит следующий шаг: `agent`, `owner`, `automation` или `none`
- `owner_action` — если `next_actor: owner`, то здесь одно конкретное действие или `none`
- `allowed_paths` — список путей, которые может менять эта задача
- `traces_to` — список этапов (например [`m01`](../milestones.md#m01), [`m02`](../milestones.md#m02)), к которым относится задача
- `implements` — включает собственный `component`; остальные связи допустимы только внутри его транзитивной цепочки требований

Опциональные поля:
- `blocker` — если `work_state: blocked`, причина блокировки
- `decides` — список `ADR_XXX`, по которым TASK является единственным владельцем подготовки сравнения, evidence и решения владельца; для обычной TASK используется пустой список или поле опускается
- `delivery_role` — допустимые значения: `component` (по умолчанию, задача поставляет внутренний компонент, заменима эквивалентной задачей) или `terminal_outcome` (задача из раздела этапа «Очередь, закрывающая пользовательский результат» — заменить её задачей со значением `component` нельзя, см. [`task_template.md`](../operations/templates/task_template.md)). Каждая TASK, упомянутая в таком разделе [`milestones.md`](../milestones.md), обязана иметь `delivery_role: terminal_outcome` — проверяется автоматически.

Пример:
```yaml
---
id: TASK_001
type: task
title: Инициализировать репозиторий и структуру проекта
component: ARC_CMP_001
work_state: planned
version: 1.0
updated: 2026-08-18
depends_on: []
next_actor: agent
owner_action: none
allowed_paths:
  - .gitignore
  - .github/
  - operations/
  - specifications/
traces_to:
  - m01
decides: []
implements:
  - ARC_CMP_001
---
```

Проверка не считает совпадение идентификаторов достаточным. Она строит цепочку `TASK → component → requirement` по каноническим `traces_to`/`implements` компонента и отклоняет требование или TEST вне этой цепочки. Полный состав этапа должен быть покрыт такими цепочками и связанными TEST до запуска этапа.

**Спецификации тестов (TEST)**:

Обязательные поля:
- `id` — формат `TEST_XXX` где `XXX` — трёхзначный номер
- `type` — значение `test`
- `spec_state` — допустимые значения: `current`, `superseded`
- `version` — номер версии
- `updated` — дата последнего изменения

Полу-обязательные поля (одно из двух):
- `title` — название теста
- `automated_evidence` или `manual_evidence` — ID доказательства (например `project_checks`, имя метода в unit тестах)

Обязательные поля продолжения:
- `execution` — как запускается тест: только `automated` или `manual`
- для `automated` требуется `automated_evidence`; для `manual` — `manual_evidence`

Опциональные поля:
- `accepts` — список этапов (например [`m01`](../milestones.md#m01)), которые этот тест подтверждает
- `traces_to` — список TASK, на которые ссылается тест
- `verifies` — список требований (SYS, SEC_CTL), которые проверяет тест

Пример:
```yaml
---
id: TEST_001
type: test
title: Проверка модели документов и трассировки
spec_state: current
execution: automated
automated_evidence: project_checks
version: 1.0
updated: 2026-08-18
accepts:
  - m01
traces_to:
  - TASK_001
verifies:
  - SYS_001
---
```

TEST содержит ровно пять разделов: «Назначение», «Что проверяется», «Автоматический запуск» либо «Действия владельца», «Критерий успеха», «Состав доказательства». История реализации и общие процедуры в карточку не добавляются.

**Доказательства качества (quality_evidence)**:

Обязательные поля:
- `id` — уникальный идентификатор, например `m01_final_report`
- `type` — значение `quality_evidence`
- `evidence_state` — допустимые значения: `incomplete`, `complete`, `invalidated`
- `version` — номер версии
- `created` — дата создания в формате `YYYY-MM-DD` (важно: используется `created`, а не `updated`)

Опциональные поля:
- `acceptance_profiles` — список профилей качества, к которым относится доказательство

Пример:
```yaml
---
id: m01_final_report
type: quality_evidence
evidence_state: complete
version: 1.0
created: 2026-08-17
acceptance_profiles:
  - foundation
---
```

Машинные записи серверного evidence используют строгую JSON-схему: `type`, `result`, 40-символьный `git_sha`, `checked_at`, непустые `environment` и `command`, числовой `exit_code`, а также непустой список артефактов с путём, размером и SHA-256. Обязательный `server_source` содержит repository, workflow, run ID, постоянный GitHub Actions URL и event SHA. Запись без любого поля, с устаревшим SHA или локально подделанным `result: passed` имеет результат `missing` и не открывает gate принятия.

**Чек-листы и процедурные документы** (работают как первичные):

Используют те же поля, что первичные документы (`id, type, document_state, version, updated, depends_on`).

Пример:
```yaml
---
id: m02_owner_checklist
type: checklist
document_state: current
version: 1.0
updated: 2026-08-18
depends_on:
  - milestones
---
```

**Генерируемые файлы** ([`project_status.md`](../project_status.md) и runtime-отчёты, не подлежат ручному редактированию):

- `id` — уникальный идентификатор генерируемого файла, например `project_status_current`
- `type` — строка `generated_*`, например `generated_owner_status`
- `generation_state` — статус генерации, обычно `generated`
- `version` — версия схемы генератора, стартует с `1.0`
- Поля `updated`, `depends_on`, `created` не используются — генерируемые файлы обновляются при каждом прогоне

Постоянный производный документ создаётся только зарегистрированным renderer из шаблона и только по пути, разрешённому [`operations/template_registry.json`](template_registry.json). Диагностические индексы и матрицы строятся по запросу в памяти или во временном каталоге и не коммитятся.

Пример:
```yaml
---
id: project_status_current
type: generated_owner_status
generation_state: generated
version: 1.0
---
```

### 8.2 Правила формирования и валидации

1. **Новые документы** создаются с версией `1.0` и текущей датой в `updated` (или `created` для доказательств).

2. **Версионирование**: младший номер (после точки) увеличивается при каждой смысловой правке документа. Старший номер меняется только по решению владельца.

3. **Зависимости (depends_on)**: должны указывать реально используемые документы. Пусто `[]` допустимо.

4. **Изменение дат**: поле `updated` проверяется при слиянии запроса — дата должна соответствовать фактическому коммиту, изменившему этот файл.

5. **Уникальные ID**: все ID должны быть уникальны в репозитории и соответствовать своему типу (TASK_XXX, TEST_XXX, ADR_XXX и т.п.).

6. **Состояния**: используются только значения, перечисленные выше. Универсальное `status` запрещено.

7. **Автоматическая валидация**: скрипт `operations/scripts/documents/check.py` проверяет корректность всех frontmatter полей при каждом коммите.

8. **Порядок полей (рекомендация, не проверяется автоматически)**: `id`, `type`, `title` (если применимо), поле состояния (`document_state`/`decision_state`/`work_state`/`spec_state`), специальные поля типа, `version`, `updated`, `depends_on` последним. Существующие документы этому порядку не всегда следуют — не переоформляйте файл только ради порядка полей при несвязанной правке.

### 8.3 Когда создавать новые документы

- **TASK** — когда требуется выполнить конкретную работу в рамках текущего этапа (не создаются для метаизменений репозитория, инструкций или шаблонов)
- **TEST** — когда требуется задокументировать способ проверки требования (автоматический или ручной)
- **ADR** — только если существует реальный значимый выбор между альтернативами (см. раздел 4)
- **Первичный документ** — когда требуется новый класс правил, требований или спецификаций
- **Доказательство качества** — автоматически генерируется агентом после фазы тестирования этапа

Не создавайте документы без явной необходимости. Предпочитайте обновление существующих.
