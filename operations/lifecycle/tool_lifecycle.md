# Жизненный цикл инструментов (Tool)

## 1. Назначение

Документ определяет, как новый `Tool` — сущность с явными полномочиями на ресурсы (файлы, сеть, секреты, внешние API) — становится частью системы через [`ARC_CMP_005`](../../specifications/architecture_baseline.md#arc_cmp_005) (Шлюз инструментов). Это дополнение к [`skill_lifecycle.md`](skill_lifecycle.md): Tool проверяется **независимо** от любого Skill, который собирается его использовать, потому что риск ресурсного доступа целиком лежит в Tool, а не в Skill, который его вызывает.

Экосистема инструментов — **закрытая навсегда**, как и у скиллов: единая точка технической авторизации — [`ARC_CMP_005`](../../specifications/architecture_baseline.md#arc_cmp_005) ("единая точка технической авторизации вызовов инструментов"), MCP и другие протоколы — только способ интеграции, не источник полномочий. Это расширяет [`SEC_CTL_011`](../../specifications/system_specification.md#sec_ctl_011) ("значимые зависимости... и интеграции проходят проверку источника, лицензии, безопасности и сопровождения") применительно конкретно к Tool.

**Статус относительно роадмапа:** как и [`skill_lifecycle.md`](skill_lifecycle.md), это процессный дизайн, подготовленный заранее. Ни в [`milestones.md`](../../milestones.md), ни в кандидатных направлениях после V1 экосистема инструментов не упомянута ни одним `BR_*`. Модели Skill/Capability/Tool в коде нет — [`ARC_CMP_003`](../../specifications/architecture_baseline.md#arc_cmp_003) ([`TASK_003`](../../work/tasks/task_003_arc_003.md), `completed`) реализует только `RuntimePort`/`Orchestrator`. Этот цикл становится действующим требованием поставки только после того, как соответствующая потребность получит `BR_*` через `requirement_wizard.py` и войдёт в состав какого-либо этапа.

## 2. Отличие от risk-модели скилла

| | Skill | Tool |
|---|---|---|
| Что это | Повторяемый сценарий, композиция Capability | Атомарная операция с явной авторизацией |
| Где риск | Косвенный (через используемые Tool) | Прямой (файлы, сеть, секреты, внешние API) |
| Что проверяется в hardening | Поведение сценария (eval, golden cases) | Фактические технические границы: не выходит ли исполнение за заявленный контракт полномочий |
| Что требует probation | Подтверждение владельца перед чувствительным действием | Подтверждение владельца перед **каждым** вызовом, вне зависимости от класса воздействия |
| Может ли быть принят "через" другую сущность | Нет — независимый цикл | Нет — независимый цикл, скилл не может его протащить (см. [`skill_lifecycle.md`](skill_lifecycle.md) Фаза 2) |

## 3. Состояния инструмента

| Состояние | Описание | Может быть заменено |
|---|---|---|
| `candidate` | Tool заявлен, проверка не начата | ✅ Да |
| `in_review` | Идёт проверка источника, лицензии, безопасности, соответствия контракту авторизации `ARC_CMP_005` | ✅ Да |
| `hardening` | Пройден review, идёт изолированная техническая отработка фактического поведения | ✅ Да |
| `probation` | Пройдена отработка, инструмент используется ограниченно с подтверждением владельца на каждый вызов | ✅ Да |
| `accepted` | Tool принят владельцем и зарегистрирован в `ARC_CMP_005` для обычного вызова | ✅ Да (супсидируется новой версией) |
| `rejected` | Tool отклонён на любой стадии проверки | ❌ Нет (исторический факт) |
| `retired` | Принятый Tool выведен из реестра (устарел, заменён, отозвано доверие к источнику, скомпрометирован) | ❌ Нет (архив) |

## 4. Жизненный цикл инструмента

### Фаза 0: Инициатива и согласование (до candidate)

Создание/подключение инструментов инициируется **только владельцем** — зеркально Фазе 0 у [`skill_lifecycle.md`](skill_lifecycle.md) и [`adr_lifecycle.md`](adr_lifecycle.md). Агент не заводит кандидата в одиночку (принцип №15 [`project_rules.md`](../../project_rules.md): "Автоматизация не подтверждает сама себе полномочия").

**Что делает агент до появления кандидата:**
- Замечает и озвучивает владельцу потребность в новом Tool: заявленная Capability не может быть закрыта уже принятым инструментом.
- Проверяет по принципу №12 [`project_rules.md`](../../project_rules.md), нет ли уже принятого Tool или зрелой библиотеки/MCP-сервера с эквивалентной, но более узкой авторизацией — новый кандидат не заводится при наличии рабочей альтернативы с меньшим объёмом полномочий.
- Излагает владельцу: какой субъект/ресурс/область/класс воздействия/данные/секреты/сеть потребуются (черновой набросок контракта [`ARC_CMP_005`](../../specifications/architecture_baseline.md#arc_cmp_005)) — как открытый вопрос, а не как готовое решение.
- Не создаёт файл/запись кандидата, пока владелец явно не подтвердил, что эту потребность стоит закрывать именно новым инструментом.

**Результат фазы:** явное решение владельца "да, заводим кандидата" — только после этого агент фиксирует `candidate`.

### Фаза 1: Заявка (candidate)

**Что делает агент при заявке:**
- Если источник внешний и пришёл как plugin-пакет (bundles hooks/subagents/MCP-серверы) — распаковывает только техническую декларацию инструмента (операция, эндпоинты, схема вызова); `hooks` и любые обработчики жизненного цикла из пакета не переносятся и не должны иметь пути к [`ARC_CMP_002`](../../specifications/architecture_baseline.md#arc_cmp_002) (Контроль владельца) или напрямую в обход [`ARC_CMP_005`](../../specifications/architecture_baseline.md#arc_cmp_005).
- Фиксирует кандидата с известным источником (`internal` или `external:<имя/URL>`) и черновым контрактом авторизации: разрешённый субъект, ресурс, область, класс воздействия, данные, секреты, сеть, ограничения, требование подтверждения, защита от дублей — по решению владельца из Фазы 0.

**Результат фазы:** зафиксированный кандидат с известным источником и черновым контрактом авторизации, готовый к технической проверке.

### Фаза 2: Проверка (in_review)

Проверяются четыре области из [`SEC_CTL_011`](../../specifications/system_specification.md#sec_ctl_011), плюс полнота контракта авторизации:

1. **Источник** — кто автор, репутация, история сопровождения.
2. **Лицензия** — совместимость с [`license_policy.md`](../policy/license_policy.md) и закрытым режимом репозитория.
3. **Безопасность** — заявленный класс воздействия (см. [`SEC_CTL_008`](../../specifications/system_specification.md#sec_ctl_008)), техническая авторизация (см. [`SEC_CTL_007`](../../specifications/system_specification.md#sec_ctl_007)), запрет секретов по умолчанию и сеть только при явной необходимости (см. [`SEC_CTL_009`](../../specifications/system_specification.md#sec_ctl_009)).
4. **Сопровождение** — воспроизводимая версия/ссылка вместо "плавающего" источника.
5. **Полнота контракта** — все поля контракта [`ARC_CMP_005`](../../specifications/architecture_baseline.md#arc_cmp_005) (субъект, ресурс, область, класс воздействия, данные, секреты, сеть, ограничения, подтверждение, защита от дублей) заданы явно, а не подразумеваются.

Tool, запрашивающий полномочия шире минимально необходимых для заявленной Capability (принцип №7 "Минимальные полномочия"), возвращается на доработку или отклоняется. Метаданные и сведения об обнаружении внешнего сервера (MCP и т.п.) остаются недоверенными данными и не расширяют заявленный контракт.

**Результат фазы:** заключение "допущен к отработке" с зафиксированным окончательным контрактом авторизации, либо `rejected` с причиной.

### Фаза 3: Отработка (hardening)

Более строгая, чем у Skill, потому что здесь проверяется фактическое, а не композиционное поведение:

- Прогон в ограниченной рабочей области ([`INF_CMP_004`](../../specifications/infrastructure_baseline.md#inf_cmp_004)), без доступа к каноническому постоянному хранилищу; квоты и управляемый жизненный цикл — как для кода/анализаторов ([`SEC_CTL_009`](../../specifications/system_specification.md#sec_ctl_009)).
- **Проверка границ, а не только штатного пути**: инструмент технически не может выйти за заявленный контракт (например: read-only Tool не может физически выполнить запись; Tool без заявленной сети не может инициировать сетевые обращения) — это проверяется активно, попыткой выхода за границу, а не только чтением документации инструмента.
- Проверка против негативных сценариев: недоступность ресурса, частичный отказ, повторный вызов (идемпотентность и защита от дублей — принцип №9 "Важные изменения должны быть обратимы").
- Проверка отсутствия скрытых побочных эффектов сверх заявленных (телеметрия, обращения к незаявленным адресам).

**Условие перехода дальше:** воспроизводимый зелёный прогон отработки, включая активную проверку границ полномочий; отчёт с доказательствами прикладывается к заявке кандидата.

### Фаза 4: Обкатка (probation)

Строже, чем у Skill: пока Tool не принят, он несёт прямой риск ресурсного доступа, поэтому:

- **Каждый** вызов инструмента в probation требует подтверждения владельца перед выполнением — вне зависимости от заявленного класса воздействия (в отличие от Skill, где подтверждение обязательно только для чувствительных действий).
- Каждый вызов проходит с повышенным уровнем аудита/логирования ([`ARC_CMP_009`](../../specifications/architecture_baseline.md#arc_cmp_009)).
- Срок обкатки определяется классом воздействия: минимум покрывает штатный путь и хотя бы один отказ/восстановление в реальных условиях.
- Любой вызов, вышедший за заявленный контракт, попытка обхода подтверждения или расхождение с заявленным поведением немедленно возвращает кандидата в `in_review` или переводит в `rejected` — обкатка не накапливает "кредит доверия" молча.

**Результат фазы:** набор реальных прецедентов использования без инцидентов и без единого выхода за контракт, обзор которых предъявляется владельцу для решения.

### Фаза 5: Принятие (accepted)

1. Агент представляет владельцу: что делает инструмент, окончательный контракт авторизации, результаты отработки и обкатки, открытые риски.
2. Только после явного решения владельца Tool переходит в `accepted` и регистрируется в [`ARC_CMP_005`](../../specifications/architecture_baseline.md#arc_cmp_005) как доступный для вызова любым принятым Skill, которому он нужен.
3. Публикация фиксируется как обычное изменение через [`change_process.md`](../change_process.md) (review + слияние в `main`).

**После принятия:**
- Вызовы больше не требуют поголовного подтверждения владельца — действует обычный контракт авторизации по классу воздействия.
- Расширение контракта (новый ресурс, более широкая область, снятие ограничения) — это новый цикл с Фазы 2 для изменённой части, а не тихое обновление на месте. Сужение контракта (владелец добровольно ограничивает уже принятый Tool) может выполняться без нового цикла — сужение полномочий не требует повторной проверки.

### Фаза 6: Отклонение (rejected)

Tool может быть отклонён на любой фазе (0–4):
- владелец не подтвердил переход из Фазы 0 в кандидата;
- источник/лицензия/безопасность не проходят проверку;
- контракт авторизации неполон или запрашиваемые полномочия шире необходимого и не сужаются по запросу;
- отработка вскрывает возможность выйти за заявленный контракт;
- обкатка вскрывает инцидент или расхождение с заявленным поведением;
- владелец отклоняет по итогам Фазы 5 без технической причины (окончательное право владельца).

`rejected` — не тупик навсегда для *потребности*: если Capability всё ещё нужна, заводится новый кандидат (другой источник/реализация/более узкий контракт) через Фазу 0.

### Фаза 7: Вывод из реестра (retired)

Принятый Tool выводится, когда:
- ни один принятый Skill больше не использует его, и Capability, которую он закрывал, больше не нужна;
- источник отозвал доверие (устарел, скомпрометирован, прекращено сопровождение) — тогда `retired` инициируется немедленно, не дожидаясь планового пересмотра;
- найдена лучшая реализация с более узким контрактом полномочий.

При выводе `Tool` в `retired` все Skill, ссылающиеся на него через `requires_tools`, автоматически теряют право вызова этого инструмента — они не остаются `accepted` "по инерции" со ссылкой на выведенный Tool; агент обязан проверить и явно сообщить владельцу, какие Skill это затрагивает.

`retired` Tool остаётся в архиве (не удаляется), ссылка на замену (если есть) фиксируется явно — аналогично `superseded_by` у ADR.

## 5. Таблица переходов состояний

```
(инициатива) ──→ candidate ──→ in_review ──→ hardening ──→ probation ──→ accepted ──→ retired
                      │              │              │              │
                      └──────────────┴──────────────┴──────────────┴──→ rejected (end)
```

| Переход | Условие | Кто принимает решение |
|---|---|---|
| (инициатива) → candidate | Владелец явно подтвердил, что потребность стоит закрывать новым инструментом (Фаза 0) | **Только владелец** |
| candidate → in_review | Заявка зафиксирована, черновой контракт авторизации известен | Агент (техническая готовность) |
| in_review → hardening | Источник/лицензия/безопасность/сопровождение проверены, контракт авторизации полон и сужен до минимума | Агент, с явной фиксацией заключения |
| in_review → rejected | Проверка не пройдена | Агент представляет причину, владелец подтверждает при спорных случаях |
| hardening → probation | Воспроизводимый зелёный прогон отработки, включая активную проверку границ | Агент |
| hardening → rejected | Отработка вскрыла возможность выйти за контракт | Агент представляет причину |
| probation → accepted | Период обкатки пройден без инцидентов и без выходов за контракт, владелец явно согласился | **Только владелец** |
| probation → rejected | Инцидент, выход за контракт или обход подтверждения во время обкатки | Немедленно, агент фиксирует, владелец уведомляется |
| accepted → retired | Потребность исчезла, источник скомпрометирован, найдена замена | Владелец (или немедленно при отзыве доверия к источнику) |

## 6. Черновой набросок полей (не формализовано)

Ниже — рабочий набросок того, какие поля потребуются кандидату инструмента, если/когда `type: tool` будет формально зарегистрирован в [`change_process.md`](../change_process.md#8-стандарт-yaml-frontmatter-и-правила-создания-файлов) §8.1 и в `operations/scripts/documents/traceability.py` (см. раздел 8 — это отдельное решение, здесь только черновик для обсуждения):

```yaml
---
id: TOL_XXX
type: tool
tool_state: candidate|in_review|hardening|probation|accepted|rejected|retired
source: internal|external:<источник>
version: 1.0
updated: <дата>
traces_to:
  - <ARC_CMP_005>
authorization_contract:
  subject: <кто может вызывать>
  resource: <над чем>
  scope: <область>
  impact_class: <SEC_CTL_008-совместимый класс>
  data: <какие данные затрагиваются>
  secrets: <какие секреты нужны, по умолчанию none>
  network: <разрешённые адреса, по умолчанию none>
  limits: <время/повторы/стоимость, см. SEC_CTL_012>
  confirmation_required: true|false
  dedup: <механизм защиты от дублей>
used_by_skills:
  - <SKL_XXX>  # заполняется по мере принятия скиллов, использующих этот Tool
retired_by: TOL_YYY  # только если tool_state: retired и есть замена
---
```

## 7. Пример сценария

### Сценарий: новый инструмент под уже согласованную Capability

```
1. Агент замечает, что Capability "работа с календарём" (согласована владельцем
   для будущего скилла) не может быть закрыта ни одним принятым Tool, и
   предлагает владельцу рассмотреть конкретный внешний календарный API —
   файл кандидата ещё не создан
2. Фаза 0: владелец подтверждает, что потребность стоит закрывать именно этим
   инструментом, с контрактом "только чтение, без права удаления событий"
3. Зафиксирован как candidate, source: external:<провайдер API>
4. Фаза 2: лицензия совместима, сопровождение активно, контракт авторизации
   полон (subject/resource/scope/impact_class/data/secrets/network/limits/
   confirmation/dedup), запрошено только чтение
5. Фаза 3: отработка в изолированной области — активно проверено, что попытка
   вызвать операцию записи технически отклоняется контрактом
6. Фаза 4: обкатка — каждый вызов подтверждается владельцем, инцидентов и
   выходов за контракт нет
7. Владелец рассматривает сводку и явно принимает инструмент
8. tool_state: accepted, Tool зарегистрирован в ARC_CMP_005; теперь Skill
   "работа с календарём" может пройти Фазу 2 своего цикла, ссылаясь на этот
   Tool как на уже accepted
```

## 8. Открытый вопрос для владельца

Как и [`skill_lifecycle.md`](skill_lifecycle.md), этот документ описывает процесс, но **не** делает `TOL_XXX` проверяемым идентификатором наравне с `ADR_XXX`/`TASK_XXX`/`SKL_XXX` — для этого нужно единое решение сразу по обеим сущностям: добавить `type: skill` и `type: tool` в [`change_process.md`](../change_process.md#8-стандарт-yaml-frontmatter-и-правила-создания-файлов) §8.1 и научить `operations/scripts/documents/traceability.py` распознавать `SKL_*`/`TOL_*` и перекрёстную ссылку `requires_tools ↔ used_by_skills`. До этого решения оба цикла — согласованный процесс, не CI-проверяемый контракт, и оба висят вне текущего роадмапа (см. раздел 1) до появления соответствующего `BR_*`.
