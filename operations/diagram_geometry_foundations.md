# Геометрические основы и общее форматирование схем

## 1. Назначение

Документ фиксирует правила, общие для **любой** SVG-схемы платформы независимо от предметной области: модульную сетку и масштаб, типографическую и интервальную прогрессию, систему выравнивания, симметрию и визуальный баланс, геометрию связей и зависимостей между узлами, цветовое кодирование, легенду, доступность и техническую гигиену SVG.

Это основа, от которой зависят предметные гайды — [`architecture_diagram_style_guide.md`](architecture_diagram_style_guide.md) (архитектурные схемы, трассируемые к `ARC_CMP_*`/`SEC_CTL_*`) и [`process_diagram_style_guide.md`](process_diagram_style_guide.md) (процессные и произвольные схемы, включая заготовки для презентаций). Предметный гайд не повторяет эти правила — он на них ссылается и добавляет только то, что специфично именно для своей категории схем (трассируемость к конкретному типу источника, формат метаданных, размещение файла).

Документ появился как отдельная сущность после того, как один и тот же геометрический материал понадобился одновременно архитектурным и процессным схемам, а часть правил (сетка, прогрессия, выравнивание, симметрия, геометрия связей) в версии 1.0/2.0 [`architecture_diagram_style_guide.md`](architecture_diagram_style_guide.md) отсутствовала вовсе — держать её отдельно от каждого предметного гайда устраняет дублирование источника истины ([`project_rules.md`](../project_rules.md) §2).

## 2. Модульная сетка и масштаб

Координаты, размеры и радиусы скругления берутся не из произвольных "круглых" чисел, а из одной задокументированной шкалы, кратной базовому модулю **4px**:

```
4 · 8 · 12 · 16 · 20 · 24 · 32 · 40 · 48 · 64 · 80 · 96 · 128 · 160
```

- Ширина/высота карточки, зазор между карточками, внутренний отступ, радиус скругления (`rx`/`ry`) — всё берётся из этой шкалы или из суммы её значений (например, зазор 40 = 32+8 допустим, зазор 37 — нет).
- Радиус скругления растёт с уровнем вложенности: внешний контейнер — 8, карточка первого уровня — 6–7, вложенная под-карточка — 4–5. Значение фиксируется один раз для каждого уровня и используется одинаково по всей схеме, а не подбирается на глаз под конкретный блок.
- Координаты не обязаны совпадать с шагом сетки абсолютно (левый край холста может быть не 0), но **интервалы между элементами** обязаны быть значениями из шкалы.

## 3. Типографическая прогрессия

Размеры шрифта — не произвольный набор чисел "чтобы отличались", а шкала с шагом ≈1.2 (малая терция) от базового размера 12px, округлённая до целого:

```
10 · 12 · 14 · 17 · 20 · 24 · 29 px
```

Рекомендуемое закрепление ролей (предметный гайд может сузить набор используемых ступеней, но не вводить размер вне шкалы):

| Ступень | Роль |
|---|---|
| 10px | Второстепенные пометки, сноски, подписи на линиях связи |
| 12px | Основной текст описаний внутри карточек |
| 14px | Заголовок под-карточки / вложенной сущности |
| 17px | Заголовок карточки верхнего уровня |
| 20px | Подзаголовок схемы, подпись слоя/раздела |
| 24px | Заголовок схемы |
| 29px | Крупный заголовок — только для схем, где заголовок — единственный доминирующий элемент листа (например, титульный слайд) |

Уже существующие схемы, размеры шрифта в которых не попадают в эту шкалу, не требуют немедленной массовой правки — миграция происходит при следующей смысловой правке той же схемы (обычном бампе `diagram_version`/аналогичного поля), а не отдельной задачей ради самой миграции (принцип №11 [`project_rules.md`](../project_rules.md): не создавать работу, не оправданную реальной необходимостью).

## 4. Интервальная прогрессия и вложенность

Отступы вложенных друг в друга уровней связаны прогрессией, а не независимым выбором на каждом уровне:

```
Внешнее поле холста        32px
Зазор между слоями/рядами  24px
Зазор между карточками     16px
Внутренний отступ карточки 12px
Зазор внутри под-элемента   8px
```

Каждый следующий уровень вложенности примерно на четверть-треть меньше внешнего — так вложенность физически читается по убыванию отступа, а не только по рамке. Предметный гайд может задать собственный набор ролей поверх этой прогрессии (например, "зазор между слоями" в архитектурной схеме и "зазор между рядами" в процессной), но обязан брать сами числовые значения из этого ряда.

## 5. Система выравнивания

Выравнивание — не только "не смешивать выключку заголовка и описания внутри одной карточки" (это необходимое, но не достаточное условие), а сквозная система на уровне всего листа:

- **Общие направляющие.** Левые края всех карточек одного ряда/слоя лежат на одной вертикальной направляющей; верхние края всех карточек одного ряда — на одной горизонтальной направляющей. Разное позиционирование внутри одного ряда допускается только тогда, когда смещение само по себе несёт смысл (например, вложенность), а не как побочный эффект произвольной раскладки.
- **ID/номер** — всегда в одном и том же углу карточки по всей схеме (например, верхний левый), с одинаковым отступом от края (см. раздел 4).
- **Подписи слоёв/разделов слева** — на одной общей вертикальной линии по всей высоте схемы.
- **Текст внутри карточки** — единая выключка для каждой текстовой роли (заголовок, описание, метка категории), одинаковая для всех карточек одной категории.

## 6. Симметрия и визуальный баланс

- Побочная ветвь/подпроцесс (например, развилка с дополнительным блоком шагов) центрируется по горизонтали (или вертикали — в зависимости от ориентации схемы) относительно точки, из которой она выходит, если это не конфликтует с правилом зазоров для связей (раздел 7). Смещение относительно триггера допустимо только как осознанное решение при нехватке места — не как случайный результат порядка добавления элементов на холст.
- Симметричные по смыслу структуры (например, два альтернативных исхода одного решения) получают зеркально симметричную раскладку, а не два визуально разных по компоновке блока.
- Скругления, толщины обводки и промежутки — консистентны по всей схеме (см. разделы 2 и 4); визуальная "тяжесть" элемента (насыщенность заливки, толщина обводки) соответствует его роли (раздел 9), а не произвольна.

## 7. Геометрия связей и зависимостей

Это самая частая причина реальных ошибок на практике (например, стрелка, прорезающая чужую карточку или текст заголовка контейнера) — правило не декларативное, а процедурное:

1. **Только ортогональная маршрутизация.** Повороты только на 90°; диагональные отрезки допустимы только как часть формы самого узла (например, грани ромба-решения), не как отрезок связи.
2. **Выделенные коридоры.** Между рядами/слоями и по внешним полям листа держится полоса, гарантированно свободная от узлов (шириной не меньше зазора между слоями, раздел 4) — именно через неё прокладываются длинные и обратные связи. Никогда не прокладывать связь напрямую через прямоугольник узла, к которому она не имеет отношения — если прямой путь пересекает чужой узел, связь обходит его по коридору, а не идёт "сквозь".
3. **Минимальный зазор.** Проложенный отрезок связи держит зазor не менее 8px (раздел 2) от границ любого узла, которому не принадлежит.
4. **Halo на пересечениях.** Если связь пересекает другую связь или текстовую подпись в открытом пространстве (не внутри чужого узла — это разрешено, раздел 6.2 architecture-специфики про пересечения), под ней рисуется более широкая обводка фона (цвет фона листа, толщина ≈3× от толщины самой линии) — это разделяет пересечения визуально без потери читаемости.
5. **Один вид стрелки — один тип отношения.** Маркер стрелки закрепляется за типом связи (поток / управление / зависимость / поддержка / возврат) и не переиспользуется для другого типа даже при визуальной нехватке вариантов — вводится новый, явно описанный в легенде стиль.
6. **Двойное кодирование связи.** Каждая связь размечается одновременно цветом **и** стилем линии (сплошная/пунктир/шаг пунктира) — нельзя различать тип связи только цветом или только пунктиром.
7. **Связь видимо исходит из реального источника.** Если по компоновочным причинам линия вынуждена пройти через координатную область другого узла на пути к цели, она не должна визуально читаться так, будто поток берёт начало в этом промежуточном узле — обходной изгиб через коридор (пункт 2) обычно и есть решение.

## 8. Легенда — обязательна и полна

Легенда обязана присутствовать и быть полной **в обе стороны**:

- каждый визуальный код, реально использованный на схеме (цвет заливки, стиль линии, паттерн/иконка категории), обязан иметь запись в легенде;
- в легенде не может быть записи, ни разу не встречающейся на самой схеме — мёртвая запись вводит в заблуждение не меньше, чем отсутствующая.

Предметный гайд определяет состав блоков легенды (например, отдельный блок "семейства ID" уместен для архитектурной схемы и обычно не нужен для процессной, если она не трассирует ID реестра).

## 9. Цветовое кодирование — по категории смысла, не только цветом

- Цвет закрепляется за категорией роли узла (например: полномочия/запреты, исполнение/проверка, данные/состояние, граница/поддержка), а не подбирается индивидуально под каждый узел. Два узла одной категории всегда получают одинаковую заливку/обводку.
- Категория **не кодируется только цветом заливки** — обязателен второй, не цветовой канал: короткая текстовая метка категории рядом с ID/номером узла, либо устойчивый паттерн обводки/иконка, закреплённые за категорией так же жёстко, как цвет. Кодирование только заливкой не читается в чёрно-белой печати и не различается при части типов дальтонизма.

## 10. Типографика, шрифты и текстовый слой

- Стек шрифтов фиксируется явно, с реальными системными fallback-шрифтами (например, `Inter, "Segoe UI", Arial, sans-serif`), либо принципиальный шрифт встраивается в SVG — схема не должна визуально "плыть" на другой ОС.
- Минимальный размер шрифта для содержательного текста — 10px по шкале раздела 3 (третьестепенные технические пометки допускают меньше только если не несут самостоятельного смысла).
- Текст никогда не выходит за границы своей карточки/плашки — переполнение решается заранее (более широкая карточка, перенос строки, короче формулировка), не наездом на соседний элемент.
- Сокращение текста через `...` с потерей смысла запрещено.
- Максимальная длина строки внутри узла — ориентировочно 40–50 символов, чтобы не требовать долгого горизонтального слежения глазом.
- Текст не конвертируется в контуры (`text-as-path`) — должен оставаться выделяемым, копируемым, доступным для скрин-ридеров и автоматических проверок.

## 11. Доступность (a11y)

- Обязательные `role="img"`, `aria-labelledby`, `<title>`, `<desc>` на корневом `<svg>` — минимум, не потолок требований.
- Контраст текста к его непосредственному фону — не ниже WCAG AA (4.5:1 для обычного текста, 3:1 для крупного от 18px полужирного или 24px обычного). Пары "цвет текста / цвет заливки категории" проверяются на контраст при выборе палитры, а не постфактум.
- Схема остаётся читаемой после масштабирования — и при увеличении (детальный просмотр), и при уменьшении до типичного превью (например, ширина ~400px). Если уменьшение превращает текст в нечитаемый шум — это повод пересмотреть плотность (раздел 12), а не публиковать схему только "для просмотра при 100%".

## 12. Охват и декомпозиция

- Один лист не должен нести больше ориентировочно **15–20** различимых узлов (значимых карточек и под-сущностей вместе). Схема, растущая сверх предела, не сжимается уменьшением шрифта — делится на обзорный лист и один или несколько детальных.
- Между обзорным и детальным листами — явная навигационная ссылка (по ID/имени, зафиксированная предметным гайдом, не по свободному тексту).
- Разбиение на несколько листов не размножает источники истины: каждая раскрываемая сущность имеет одну "домашнюю" схему с полной детализацией; на остальных листах она — свёрнутая ссылка.

Предметный гайд может уточнить порог плотности под свою категорию (например, для слайда презентации порог значительно ниже — см. [`process_diagram_style_guide.md`](process_diagram_style_guide.md) раздел про PPTX-вариант).

## 13. Техническая гигиена SVG

- Фиксированный `viewBox`, согласованный с `width`/`height` — без скролла и обрезки контента.
- Единая типографическая шкала через CSS-классы (раздел 3) — один класс, один размер/вес во всей схеме, не разрозненные инлайновые `font-size`.
- Явные XML-комментарии в исходном коде схемы, фиксирующие использованные значения отступа/сетки для нового блока — облегчает проверку соответствия разделу 2 при последующей правке.

## 14. Чек-лист общих требований

Предметный гайд подключает этот список к своему собственному чек-листу, а не дублирует пункты:

1. Все координаты/размеры/радиусы — из шкалы раздела 2; все размеры шрифта — из шкалы раздела 3; все отступы — из прогрессии раздела 4.
2. Общие направляющие выравнивания выдержаны (раздел 5); симметричные по смыслу структуры визуально симметричны (раздел 6).
3. Ни одна связь не проходит через чужой узел или чужой текст; пересечения в открытом пространстве — с halo; один вид стрелки — один тип отношения; связь размечена цветом и стилем одновременно (раздел 7).
4. Легенда полна в обе стороны (раздел 8); категория узла кодируется цветом и вторым каналом (раздел 9).
5. Шрифтовой стек фиксирован; текст не переполняет узлы, не обрезан многоточием, не переведён в контуры (раздел 10).
6. `role="img"`, `aria-labelledby`, `<title>`, `<desc>` на месте; контраст — не ниже WCAG AA; схема читаема в уменьшении (раздел 11).
7. Плотность узлов не превышает порог; при превышении — разбиение на обзорный и детальные листы с навигацией между ними (раздел 12).
8. `viewBox` согласован с `width`/`height`; типографика — через CSS-классы (раздел 13).
