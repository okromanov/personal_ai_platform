# Правила оформления и структурирования архитектурных схем

## 1. Назначение

Документ фиксирует обязательные правила подготовки новых архитектурных SVG-схем платформы, извлечённые из разбора `personal_ai_platform_architecture.svg` (ветка `codex/architecture-scheme-hierarchy`, `work/artefacts/architecture/`). Часть правил закрепляет удачные приёмы этой схемы как обязательный стандарт; часть — прямой запрет на конкретные ошибки, найденные в ней при разборе точности, единообразия и корректности текста.

Схема — это производное представление [`architecture_baseline.md`](../specifications/architecture_baseline.md) и [`system_specification.md`](../specifications/system_specification.md), а не отдельный источник истины ([`project_rules.md`](../project_rules.md) §2: "Один и тот же смысл не должен иметь два равноправных источника истины"). При расхождении схемы и спецификации побеждает спецификация, а схема считается устаревшей и требует правки.

## 2. Структура листа

- Фиксированный `viewBox`, совпадающий с `width`/`height` — без скролла и обрезки контента.
- Обязательные `role="img"` и `aria-labelledby` на корневом `<svg>`, с `<title>` и `<desc>` внутри — не декоративная картинка, а размеченный для доступности документ.
- Единый header-блок в фиксированном порядке: заголовок схемы → подзаголовок → блок легенды. Заголовок — существительное/именная группа, описывающая охват схемы, не предложение.
- Единая типографическая шкала через CSS-классы (`.title`, `.component-title`, `.small-text` и т.п.), а не разрозненные инлайновые `font-size`. Один класс — один размер/вес во всей схеме.
- Отступы внутри карточек и между слоями выражаются небольшим фиксированным набором значений (например, 20/22/28 px), а не подбираются на глаз под каждый элемент — это упрощает добавление новых карточек без визуального дребезга.

## 3. Легенда — обязательна и полна

Легенда — три независимых блока, и каждый визуальный код, используемый где-либо в схеме, обязан присутствовать в соответствующем блоке:

1. **Смысл заливки карточек** — что означает каждый цвет заливки/обводки (категория компонента).
2. **Смысл стилей связей** — что означает каждая комбинация цвета линии + штриховки (сплошная/пунктир, шаг пунктира) + вид стрелки.
3. **Семейства идентификаторов** — что означает каждый префикс ID (`ARC_CMP_*`, `ARC_FLOW_*`, `INF_CMP_*`, `SEC_CTL_*` и т.п.), встречающийся на схеме.

Правило проверки перед публикацией: пройтись по каждому уникальному цвету заливки, каждому уникальному сочетанию цвет+пунктир линии и каждому префиксу ID, реально использованному в SVG, и убедиться, что для него есть запись в легенде. Визуальный код без записи в легенде запрещён.

## 4. Цветовое кодирование — по категории смысла, не по компоненту

Цвет закрепляется за **категорией роли** компонента, а не подбирается индивидуально под каждый компонент:

- Полномочия и запреты (контроль владельца, аварийный выключатель, отклонённый/контролируемый исход) — один цвет во всей схеме.
- Исполнение и проверка (оркестрация, шлюзы, проверка качества) — другой цвет.
- Данные и состояние — третий цвет.
- Граничные/поддерживающие узлы (владелец, каналы, эксплуатация) — нейтральный/белый.
- Физическое размещение/инфраструктура — визуально обособленный (например, тёмная заливка), поскольку это качественно другой уровень, а не ещё один логический слой.

Два компонента одной категории всегда получают одинаковую заливку/обводку — если требуется различать их дальше, используется не новый цвет, а надпись/иконка внутри уже закреплённого цвета категории.

## 5. Связи и потоки

- Каждая связь размечается **и цветом, и стилем линии** (сплошная/пунктир/шаг пунктира) одновременно — нельзя различать типы связей только цветом (не читается в ч/б печати и для дальтоников) и нельзя различать только пунктиром без цвета (не читается при пересечении многих линий).
- Каждая содержательная связь несёт подпись с её ID из спецификации (`ARC_FLOW_00X · короткое имя шага`), размещённую прямо на линии в отдельном плашке — стрелка без опоры на `ARC_FLOW_*` в спецификации не подписывается номером (не изобретайте номер потока, которого нет в источнике).
- Сквозные связи, пересекающие несколько слоёв (аварийный выключатель, поддержка инфраструктуры, возврат результата через канал), рисуются отдельными "рельсами" сбоку, а не повторяющейся стрелкой в каждую отдельную карточку. Если такая линия пересекает другие связи, под ней даётся более широкая обводка фона (halo) того же цвета, что фон листа — это разделяет пересечения визуально.
- Линия связи обязана визуально начинаться от реального источника потока. Если по компоновочным причинам линия вынуждена проходить через область другого слоя, это не должно читаться так, будто поток берёт начало в этом промежуточном слое — при необходимости добавляется явный обходной изгиб или примечание, а не прямой отрезок через чужую карточку.

## 6. Карточки компонентов — единая анатомия

Все карточки одной категории имеют одинаковую внутреннюю структуру и порядок элементов:

1. ID компонента/потока (мелкий текст, верхний левый угол) — если применимо.
2. Заголовок (крупный, полужирный).
3. Краткое описание (1 строка сути компонента).
4. Опциональные вложенные под-карточки (сущности/подкомпоненты) — с тем же принципом: одинаковый визуальный стиль для сущностей одного логического уровня.

Слои схемы нумеруются по **фактическому логическому потоку выполнения** (например: владелец → интерфейсы → контроль → состояние → исполнение → …), а не по порядковому номеру `ARC_CMP_*` в реестре спецификации — номер реестра и номер слоя на схеме принципиально разные вещи и не обязаны совпадать. Если это может ввести читателя в заблуждение, внизу схемы даётся явная сноска об этом (см. раздел 9).

## 7. Трассируемость к спецификации — обязательна и точна

- Каждый компонент/поток, изображённый на схеме, подписывается точным ID из [`architecture_baseline.md`](../specifications/architecture_baseline.md)/[`system_specification.md`](../specifications/system_specification.md) (`ARC_CMP_*`, `ARC_FLOW_*`, `SEC_CTL_*`, `INF_CMP_*`, `INF_FLOW_*`) — не перефразированным именем и не сокращением.
- **Если спецификация явно задаёт порядок или цепочку зависимости между сущностями (запись вида `A → B → C` в тексте документа), визуальный порядок на схеме обязан буквально совпадать с этим порядком.** Найденная ошибка для образца: [`architecture_baseline.md`](../specifications/architecture_baseline.md) (раздел [`ARC_CMP_003`](../specifications/architecture_baseline.md#arc_cmp_003)) прямо задаёт цепочку `навык → возможность → инструмент → реализация/поставщик` (Skill → Capability → Tool → Implementation), а схема отрисовала первые два элемента в обратном порядке (Capability → Skill). Перед публикацией переставленный относительно спецификации порядок — блокирующая ошибка, а не стилистический выбор.
- Перед публикацией схемы для каждого упомянутого на ней ID выполняется точечная сверка: открыть соответствующий раздел спецификации и убедиться, что название узла на схеме и его краткое описание не расходятся по смыслу с текстом раздела (а не только совпадают номером).

## 8. Язык и терминология — единообразие обязательно

- Схема пишется **полностью на одном языке** (русском, вслед за спецификациями). Если сущность в спецификации имеет параллельное англоязычное имя (например, `Capability`/`Skill`/`Tool`/`Implementation` в модели [`ARC_CMP_003`](../specifications/architecture_baseline.md#arc_cmp_003)), либо переводится последовательно везде на схеме, либо оставляется на языке оригинала последовательно везде — **смешивание в пределах одной схемы запрещено**. Найденная ошибка для образца: блок сущностей `Capability/Skill/Tool/Implementation` и все их описания были на английском, тогда как остальные ~95% текста схемы — на русском.
- Для одного и того же понятия используется **ровно один** русский термин по всей схеме, совпадающий с термином из заголовка соответствующего раздела спецификации — синонимы для одной и той же сущности запрещены, даже стилистически уместные. Найденная ошибка для образца: один и тот же контроль ([`SEC_CTL_002`](../specifications/system_specification.md#sec_ctl_002)) был назван на одной схеме тремя разными способами — "Kill Switch" (в карточке), "аварийная остановка" (в подписи линии) и "аварийный выключатель" (термин из спецификации) — при подготовке новой схемы термин берётся из заголовка раздела спецификации и используется этим же словом везде, где встречается.

## 9. Пояснительные сноски

Внизу схемы фиксируются краткие интерпретационные оговорки, если что-то на схеме может быть прочитано неверно без такой оговорки. Примеры уместных сносок:
- нумерация слоёв — это порядок логического потока, а не порядок ID в реестре спецификации;
- логический компонент не означает отдельный процесс/контейнер/сервис (принцип №9 [`architecture_baseline.md`](../specifications/architecture_baseline.md#2-архитектурные-принципы): "Модульный монолит по умолчанию").

Сноска не заменяет исправление самой схемы там, где неоднозначность можно устранить оформлением (раздел 6) — она нужна только для случаев, где сама природа схемы (двумерная плоскость для многомерных отношений) не позволяет устранить неоднозначность иначе.

## 10. Чек-лист перед публикацией

1. Каждый визуальный код (цвет заливки, стиль линии, префикс ID) присутствует в легенде (раздел 3).
2. Цвет заливки одинаков для всех компонентов одной категории (раздел 4).
3. Каждая связь размечена и цветом, и стилем линии; содержательные связи подписаны `ARC_FLOW_*`/`INF_FLOW_*` (раздел 5).
4. Каждый ID на схеме сверен построчно с текстом соответствующего раздела спецификации, включая заданный спецификацией порядок/цепочку зависимостей (раздел 7).
5. Весь текст на одном языке; для каждого понятия использован ровно один термин, совпадающий с заголовком раздела спецификации (раздел 8).
6. Ни одна связь визуально не выглядит начинающейся не из того слоя, из которого она реально исходит (раздел 5).
7. Заголовок, подзаголовок и сноски не противоречат содержанию текущей версии специфицированных документов на момент публикации.
