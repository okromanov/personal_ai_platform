# Шаблон TASK

Шаблон применяется только к работе, которая двигает этап и поставляет результат проекта. Для изменения репозитория, [`operations/change_process.md`](../change_process.md), инструкций агента, шаблонов или внутренних проверок TASK не создаётся.

Все требуемые поля frontmatter должны соответствовать стандарту, описанному в [`operations/change_process.md#82`](../change_process.md).

```markdown
---
id: TASK_XXX
type: task
title: <Название>
component: <ARC_CMP/ARC_FLOW/INF_CMP/INF_FLOW ID>
work_state: planned
version: 1.0
updated: <yyyy-mm-dd>
depends_on:
  - TASK_<непосредственно предыдущая>
next_actor: agent
owner_action: none
owner_followups: []
allowed_paths:
  - work/tasks/task_xxx_<short_name>.md
  - <точный путь или шаблон каталога>
traces_to:
  - mXX
implements:
  - <тот же component ID>
---

# TASK_XXX — <Название>

## 1. Зачем это делаем

## 2. Результат

## 3. Где мы сейчас

## 4. Что делать сейчас

### Агенту

Одно конкретное следующее действие или короткий список.

## 5. План выполнения

- [ ] Шаг 1
- [ ] Шаг 2
- [ ] Проверка результата и покрытия изменённых путей

## 6. Состав

Указать границы работы и соответствующие `allowed_paths`. Если работа заблокирована, установить `work_state: blocked` и добавить одно поле `blocker` с конкретной причиной.

## 7. Проверки и доказательства

Для запроса на слияние автоматическая проверка должна подтвердить, что все пути поставки продукта входят в `allowed_paths` активной либо изменяемой TASK.

Связанный TEST проверяет требования из канонической цепочки собственного `component`. Ссылка на несвязанный SYS/BR/SEC/INF не считается покрытием.

## 8. Готово когда

## 9. Что будет дальше

## 10. Что это даёт владельцу
```

Раздел «10. Что это даёт владельцу» — 1-3 предложения на бытовом языке, без имён классов, файлов и модулей, о том, что владелец теперь может делать благодаря этой TASK (например: «Можно написать боту в Telegram и получить отслеживаемую задачу вместо потерянного сообщения»). Для ещё не начатой TASK допустим общий плейсхолдер («Функционал появится после завершения этой TASK»); при завершении TASK раздел обязателен и не может оставаться этим плейсхолдером — автоматическая проверка `tasks` это отклоняет. Раздел цитируется целиком в [`project_status.md`](../../project_status.md) в разделе «Что уже умеет решение», поэтому в нём не должно быть относительных ссылок (см. правило [`AGENTS.md`](../../AGENTS.md#38-гиперссылки-в-документации)).

Раздел «8. Готово когда» — проверяемый список условий, а не пересказ плана. Каждый пункт должен быть однозначно да/нет: конкретная команда и её результат («operations/tests/product/test_channels.py: N/N тестов прошли»), а не общая фраза без числа или ссылки на артефакт. Для ещё не начатой TASK допустим общий список («Все шаги плана выполнены», «CI успешен» и т.д.); при завершении он конкретизируется фактическими числами и путями, как в [`TASK_001`](../../work/tasks/task_001_arc_001.md).

Путь поставки продукта добавляется в активную TASK до его изменения. Завершённая TASK может покрывать разницу только при изменении её собственной карточки в той же разнице. Служебные и производные файлы отдельно перечислять не требуется.

Новая TASK получает следующий номер без пропуска и добавляется в конец очереди. Поле `depends_on` обязательно содержит непосредственно предыдущую TASK. Исключение — [`TASK_001`](../../work/tasks/task_001_arc_001.md), у которой предыдущей карточки нет. Текущей считается первая незавершённая карточка; одновременно выполняемой или заблокированной может быть только одна TASK.

Если следующий шаг должен выполнить владелец, `next_actor` меняется на `owner`, `owner_action` получает одно конкретное действие, а подраздел `### Агенту` заменяется на `### Владельцу`. При `owner_action: none` подраздел владельца запрещён.

`owner_followups` — необязательный список **некритичных** для дальнейшей работы действий владельца, не связанный с `next_actor`/`work_state`: в отличие от `owner_action`, такой пункт может оставаться открытым и на `completed` TASK, не блокируя очередь и не удерживая TASK в промежуточном состоянии. Front matter поддерживает только плоские списки строк (без вложенных объектов), поэтому каждый элемент — одна строка вида `"[open] <действие>"` или `"[done] <действие>"`. Пока есть хотя бы один элемент со статусом `open`, его текст действия (без префикса `[open] `) дословно повторяется в разделе `## Незакрытые действия владельца` карточки (раздел запрещён, если открытых пунктов нет), а также автоматически появляется в общем списке [`project_status.md`](../../project_status.md). Пример: проверка, которую агент не может выполнить сам (нет нужного окружения) и которая не отменяет того, что сама TASK готова и сдана.

```markdown
owner_followups:
  - "[open] Собрать docker-образ и подтвердить, что health-check проходит (см. §11 инструкции)."
```

Завершённая TASK имеет `work_state: completed` сразу после выполнения работы и проверок. Принятие этапа не удерживает TASK в промежуточном состоянии.

Каждое упоминание в тексте карточки элемента из [`generated/traceability_matrix.md`](../../generated/traceability_matrix.md) (`BR_XXX`, `SYS_XXX`, `THR_XXX`, `SEC_CTL_XXX`, `ARC_CMP_XXX`, `ARC_FLOW_XXX`, `INF_REQ_XXX`, `INF_CMP_XXX`, `INF_FLOW_XXX`, `ADR_XXX`, другой `TASK_XXX`/`TEST_XXX`, этап `mXX`) оформляется как код-спан и ссылка на исходный документ — `` [`SYS_001`](../../specifications/system_specification.md#sys_001) `` для элемента спецификации, `` [`TASK_002`](../../work/tasks/task_002_arc_002.md) `` для другой карточки. Исключение: разделы «2. Результат» и подраздел «### Агенту»/«### Владельцу» раздела «4. Что делать сейчас» цитируются целиком в [`project_status.md`](../../project_status.md) на уровне корня репозитория — относительная ссылка, посчитанная для `work/tasks/`, там ведёт мимо проекта, поэтому в этих двух местах элементы оставляют без ссылки (обычным код-спаном).
